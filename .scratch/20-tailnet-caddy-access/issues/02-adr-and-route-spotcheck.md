## Notes

See epic 20 spec, "Further Notes" and "Out of Scope". Two side-findings from this epic's investigation are explicitly *not* this ticket's scope, but should be noted in the ADR so they aren't lost:

- `owntracks-ui.<secret-silverbullet-domain>` currently has a public/Cloudflare-proxied DNS record despite being a `tailnet_only` route, which independently makes it unreachable by anyone via that hostname (Cloudflare's edge IP never matches the tailnet subnet either) — an operator/DNS-console question, not something this epic's code touches. **Update, at ticket #02 time**: this is no longer the current state — see Implementation notes below; kept here verbatim as the historical record of what this epic's original investigation found, not silently corrected.
- Whether that DNS record should exist at all, and whether other `tailnet_only` routes should or shouldn't have public DNS records, is out of scope for this epic entirely.

## Implementation notes

- **ADR**: `docs/adr/0005-tailnet-proxy-protocol-relay.md`. Follows this repo's established ADR format (Status/Context/Decision/Consequences/References, matching ADR-0004's shape). Documents all four points the ticket asked for, plus both side-findings from the Notes section above (recorded in Context, not folded into Decision/Consequences, matching how they're scoped here — noted, not resolved).
- **Route spot-check, live on the real VPS**, all 5 routes:
  - `monitor` (`tailnet_only`) and `adguard` (`tailnet_only`) already have DNS records pointed directly at the VPS's own Tailscale IP (an operator workaround applied during this epic's live debugging, before the fix existed). `owntracks-ui` (`tailnet_only`) also now resolves to the VPS's Tailscale IP, **not** the public/Cloudflare-proxied record the epic's original investigation found (see this ticket's own Notes section above and the epic spec's Further Notes) — the record was evidently repointed by the operator at some point between that investigation and this ticket. All three tested via their real hostnames directly; ADR-0005's Context reflects this current state.
  - `wiki` (`mfa_auth`) and `dash` (`mfa_auth`) keep their normal Cloudflare-proxied public DNS records — tested via `curl --resolve <host>:443:<tailscale-ip>` to force the tailnet path specifically (their real DNS doesn't route there).
  - Results, all confirmed via Caddy's own access log showing the real tailnet peer address (`remote_ip: <tailnet-ip>`, not a masqueraded/bridge address) for every request: `monitor` → 200, `owntracks-ui` → 200, `wiki` → 200 (no Authelia redirect — `mfa_auth` correctly skipped). `adguard` and `dash` both returned 302 — verified via response headers this is each app's OWN internal login redirect (`Location: /login.html` for AdGuard's web UI, `Location: /login?next=%2F` for Hermes-agent's dashboard), not an Authelia challenge — exactly the expected "reached the app directly, no MFA gate" behavior for a tailnet source, just surfaced as each app's normal unauthenticated-session redirect rather than a bare 200 on `/`.
- **Operator-facing docs, investigated and none needed**: the relay requires no manual step at all — `tailscale ip -4`/`-6` are queried automatically at deploy time (ticket #01), the shared socket directory is provisioned automatically (`wiki_volume`'s `ensure_directory`), and no new credential is generated by a system this playbook just deployed (the pattern every existing "Manual Post-Deploy Steps" README entry shares). Checked the firewall angle specifically, since `caddy-relay` binds a new address (`<tailscale-ip>:443`): `roles/tailscale/tasks/main.yml`'s "Allow the Tailscale VPN interface" UFW rule already allows ALL inbound traffic on the `tailscale0` interface unconditionally (not scoped to specific ports) — so a new service binding a Tailscale-interface address needs no new UFW rule, this one included. No README changes made.
