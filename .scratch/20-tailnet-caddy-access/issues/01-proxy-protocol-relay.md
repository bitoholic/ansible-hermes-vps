# 01: Add the tailnet-facing PROXY-protocol relay and Caddy's internal listener

**What to build:** A real Tailscale client reaching any `mfa_auth`- or `tailnet_only`-gated hostname (`wiki`, `dash`, `owntracks-ui`, `adguard`, `monitor`) via the VPS's own Tailscale IP gets correctly recognized as a tailnet source — `mfa_auth` routes skip the Authelia challenge, `tailnet_only` routes actually load instead of 404ing — while every public-internet and Cloudflare-proxied client's existing, already-correct behavior is completely untouched.

**Blocked by:** None (can start immediately)
**Blocks:** #02

**Status:** ready-for-agent

- [x] A new host-networked relay component binds to the VPS's Tailscale IP (both v4 and v6) on port 443, accepts the raw TCP connection, and forwards it to Caddy with a PROXY protocol header carrying the real client IP (port 80 turned out not to need this — see Implementation notes)
- [x] Caddy's public port-publish for 443 is narrowed to the VPS's public IP specifically (no longer all-interfaces), freeing that same port on the Tailscale IP for the relay
- [x] ~~Caddy's Dockerfile compiles in a PROXY-protocol-terminating module~~ — investigated and found unnecessary: `caddy.listeners.proxy_protocol` already ships natively in the pinned Caddy version (2.11.4), confirmed by actually building the image and checking `list-modules` — see Implementation notes for the real dead-end this ticket hit first
- [x] Caddy gains a second, internal-only listener (loopback-bound, never published to the Docker bridge's externally-reachable side or the public internet) that trusts and terminates PROXY protocol from the relay only; the existing public-facing listener's configuration is provably unchanged — no PROXY-protocol wrapper, no new trust surface
- [x] Both `mfa_auth`'s and `tailnet_only`'s `not remote_ip` matchers check `tailscale_subnet_v6` alongside the existing v4 constant, closing the pre-existing v4-only gap surfaced during this epic's investigation
- [x] Port 8443 (matrix/owntracks) is untouched — confirmed no PROXY-protocol dependency or listener change applies there
- [x] Each service's own raw published port (Beszel's 8090, AdGuard's 3001) is confirmed still reachable over Tailscale exactly as before, unaffected by this change
- [x] The fix is verified against the real VPS: a real client reaching `monitor.<secret-silverbullet-domain>` via the VPS's Tailscale IP loads correctly (200, real `remote_ip` in Caddy's access log), `wiki.<secret-silverbullet-domain>` correctly skips the Authelia challenge over the same path (200, no redirect to `auth.<secret-silverbullet-domain>`), and both routes' public-IP behavior is confirmed unchanged (still 404 / still MFA-redirected)

## Notes

See epic 20 spec, "Solution" and "Implementation Decisions". Two decisions are explicitly left open for this ticket to resolve, not pre-decided by the spec:

- **How the VPS's public IP and its own Tailscale IP(s) are obtained at deploy time** — no existing variable holds either today. Candidates the spec names: Ansible's own gathered facts (`ansible_default_ipv4.address`, `ansible_tailscale0.ipv4.address`/`ansible_tailscale0.ipv6`) versus a manually-set `group_vars` value versus parsing `tailscale ip`/`tailscale status --json` directly. Whichever is chosen must work reliably under `--check` and must account for `tailscale0` not existing as an interface until the `tailscale` role's own "bring up Tailscale" task has already run in the same play.
- **The exact relay tool** — the spec suggests HAProxy in TCP mode (`send-proxy`/`send-proxy-v2`) as the natural fit, but leaves the final choice to this ticket.

PROXY-protocol trust is a hard security boundary (see spec's Implementation Decisions): getting the internal listener's reachability wrong would let anyone on the public internet forge a PROXY header claiming a `100.64.0.0/10` source and fully bypass both `mfa_auth` and `tailnet_only`. Treat the "public listener has no PROXY-protocol wrapper" test as the single most important regression guard this ticket adds, not a minor config nit.

Live verification (the last checkbox) cannot be satisfied by a rendering-only test — there is no real Tailscale network, masquerade behavior, or PROXY-protocol handshake available outside a real deploy. Static tests should cover everything else (compose-fragment shape, Dockerfile module presence, the loopback-only/no-public-wrapper regression guard, the v6 matcher extension, and that every existing gateway-render assertion still passes unchanged).

## Implementation notes

Both open decisions were resolved:
- **IP sourcing**: the VPS's public IP uses `ansible_default_ipv4.address` (already gathered, no new task needed). The Tailscale IP(s) are queried via `tailscale ip -4`/`tailscale ip -6` (not `ansible_tailscale0.*` facts — more explicit and doesn't depend on how reliably Ansible's generic interface-fact-gathering parses a WireGuard-style `/32` point-to-point interface), added to `roles/tailscale/tasks/main.yml` immediately after "Bring up Tailscale", with `ignore_errors: "{{ ansible_check_mode }}"` and an empty-string fallback since `command` tasks don't run under `--check`.
- **Relay tool**: HAProxy (`haproxy:3.4-alpine`, `network_mode: host`, `send-proxy-v2`), matching the spec's own suggestion.

Several real problems surfaced only by actually building/deploying, not by reasoning about the design — each fixed and verified live before moving on:

1. **Caddy needs no Dockerfile change at all.** The spec (after its own first-round correction) said `caddy.listeners.proxy_protocol` requires an `xcaddy` build, based on Caddy's own module docs. Building it via `xcaddy build --with github.com/mastercactapus/caddy2-proxyprotocol` on the real VPS panicked at runtime with `module already registered: caddy.listeners.proxy_protocol` — Caddy adopted native PROXY-protocol support as a built-in module at some point before 2.11.4 (the version this repo already pins), after the third-party module and Caddy's own docs page were written. Confirmed via `caddy list-modules` against the real, unmodified `caddy:2.11.4` image. The Dockerfile is untouched by this ticket.
2. **Port 80 doesn't need the relay.** It only ever serves Caddy's automatic HTTP→HTTPS redirect, which fires before any `mfa_auth`/`tailnet_only` matcher runs — narrowed scope to port 443 only, simplifying the relay/listener design from what the spec first described.
3. **HAProxy's official image can't bind port 443 as its own non-root `USER haproxy`.** `cap_add: NET_BIND_SERVICE` alone doesn't fix this — confirmed via `docker inspect` that the capability WAS correctly granted at the container level, yet binding still failed with `Permission denied` (the image's own `USER haproxy` Dockerfile directive means the entrypoint never runs as root at all, so there's nothing for the capability to attach to). `network_mode: host` also rules out the commonly-suggested `--sysctl net.ipv4.ip_unprivileged_port_start=0` alternative (scoped per network namespace, which a host-networked container shares with the host entirely). Fixed via HAProxy's own standard, designed-for pattern: `user: root` at the container level, then `user haproxy` / `group haproxy` (plus `chroot /var/empty`, silencing HAProxy's own runtime hardening warning) in `haproxy.cfg`'s `global` section — the master process binds every socket as root, then drops privileges immediately after.
4. **The `allow` restriction was too narrow and silently defeated the entire fix.** The first live end-to-end test (`curl` through the relay to `monitor.<secret-silverbullet-domain>`) still showed `remote_ip: 172.22.0.1` in Caddy's access log — a 404, not the expected 200. Root cause: caddy-relay's own connection to Caddy's internal listener *also* transits Docker's port-publish NAT (`127.0.0.1:8543:8543`), which rewrites its source to the `gateway` network's bridge address, not literal `127.0.0.1` — so the `allow 127.0.0.1/32 ::1/128` restriction correctly (per its own security design) refused to trust the PROXY header from an unrecognized peer and fell back to the raw, NAT'd address. Fixed by widening `allow` to include `172.16.0.0/12` (Docker's entire default bridge address pool, not today's specific `/16`, which isn't a stable value). Re-verified live: `remote_ip` now shows the real address, status 200.
5. **A Caddyfile/haproxy.cfg content-only change doesn't take effect on its own.** `docker compose up`'s own change-detection does not recreate a container just because a bind-mounted file's content changed on disk, only when the service definition itself changes — every past Caddyfile change in this repo's history happened to also touch the compose fragment (a port move, a new env var), which masked this gap until this ticket's fix #4 above needed a Caddyfile-only redeploy. Fixed properly, not just patched around: added `roles/gateway/handlers/main.yml` (new file — this role never had handlers before) with `Restart caddy`/`Restart caddy-relay` handlers, notified from their respective `ansible.builtin.template` tasks. Handlers run at the end of the play, after the docker role's stack-start step has already ensured the container exists, so this is safe on both a first-ever deploy (harmless extra restart) and a subsequent config-only change (the actual fix).

Every fix above was verified against the real VPS before moving to the next: rebuilding the Dockerfile, checking `list-modules`, watching the actual crash-loop logs, and re-running the same `curl` + Caddy-access-log check after each change until the real source IP was correctly recognized end-to-end, for both a `tailnet_only` route (`monitor`, 200) and an `mfa_auth` route (`wiki`, 200, no Authelia redirect) — with the public-IP path for both confirmed unchanged (still 404 / still MFA-redirected) as the essential negative check.
