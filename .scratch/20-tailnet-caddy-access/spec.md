# Spec: Preserve Real Source IP for Tailscale Clients Reaching Caddy by Hostname

> Status: ready-for-agent
> Source: Epic 20 — discovered while operator-validating epic 19's live deploy: `monitor.<domain>` (a `tailnet_only` route, epic 18) 404'd for the operator despite connecting over Tailscale, once its DNS record was pointed at the VPS's own Tailscale IP.
> Related: **Does not supersede or contradict ADR-0001** (source-based MFA) or epic 18's `tailnet_only` route type — both remain the correct *design intent*; this epic fixes the network-layer mechanism that intent depends on, which turns out not to hold for one specific access path. `19-cloudflare-proxied-ingress` (matrix/owntracks, port 8443 — confirmed unaffected and explicitly out of scope, see below). `12-add-custom-services` (origin of `mfa_auth`); `18-second-wave-custom-services` (origin of `tailnet_only`).
> Vocabulary: "tailnet-facing access" (a client reaching a Caddy-fronted hostname via the VPS's own Tailscale IP, as opposed to its public IP or a Cloudflare-proxied IP), "source-based access control" (the umbrella term for both `mfa_auth`'s bypass and `tailnet_only`'s hard-block, since both key off Caddy's `remote_ip` for the same `tailscale_subnet` constant), "hairpin NAT / local-subnet masquerade" (a Tailscale-specific netfilter behavior, not a Docker one, that rewrites a Tailscale peer's source IP when its traffic is forwarded to a service on the *same host* it connected to), "PROXY protocol" (a TCP-layer protocol that prepends a small header stating the original source/destination address before the real payload, letting a downstream server recover a client IP that an upstream relay/load-balancer would otherwise have replaced via NAT — Caddy can terminate it, but only via `caddy.listeners.proxy_protocol`, a **non-standard module** not included in the stock Caddy binary; verified directly against Caddy's own module documentation, which states outright that it "does not come with Caddy" and must be added via `xcaddy`).

## Problem Statement

Both of this repo's source-IP-based access controls — `mfa_auth`'s "Tailscale clients skip Authelia" bypass (ADR-0001) and `tailnet_only`'s hard 404-block for non-Tailscale sources (epic 18) — assume Caddy can see a connecting Tailscale client's real `100.64.0.0/10` address. That assumption silently doesn't hold for one specific, real access path: a client connecting to a Caddy-fronted hostname whose DNS record resolves to the **VPS's own Tailscale IP**.

Diagnosed live, during epic 19's deployment: the operator added a DNS record for `monitor.<domain>` pointing at the VPS's Tailscale IP, then got a self-signed-cert warning (expected — `tailnet_only` routes use the internal CA) followed by a 404 (not expected — the operator was genuinely connecting over Tailscale). Caddy's own access log showed the connection's `remote_ip` as `172.22.0.1` — the Docker bridge gateway address for the `gateway` network, not the operator's real Tailscale IP. Root cause, confirmed via the VPS's own `iptables -t nat -L ts-postrouting`: Tailscale installs its own netfilter rule that masquerades a peer's traffic when that traffic is being forwarded to a service on the *same host* the peer connected to (a documented Tailscale behavior for exactly this "peer reaches this machine's own locally-hosted service" case — the original source IP is not preserved anywhere Caddy can read it; it is genuinely gone by the time the packet reaches the container, not merely hidden behind a header Caddy could inspect). This is a Tailscale-level behavior, independent of and unrelated to Docker's own `DOCKER-USER` filtering chain (which already correctly enforces port-class access — this bug is upstream of that, at the point where Caddy tries to *identify* a source, not *permit* it).

Confirmed **not** an isolated `monitor`-only issue: the same masquerade applies to any Docker-published port reached via `tailscale0`, so it affects every route gated by `remote_ip {{ tailscale_subnet }}` — both `tailnet_only` routes (`owntracks-ui`, `adguard`, `monitor`) and `mfa_auth`-gated routes (`wiki`, `dash`) whenever reached via the VPS's Tailscale IP. It does **not** affect: traffic reaching those same hostnames via their public IP or Cloudflare's proxy (never traverses `tailscale0`, so no masquerade — and correctly gets MFA-challenged/404'd there, since that traffic genuinely isn't from a trusted network); each service's own raw "belt-and-suspenders" published port (`beszel-hub:8090`, `adguard:3001`) reached directly over Tailscale, since those have no source-IP gate of their own to break; or `matrix`/`owntracks` on port 8443 (epic 19), since neither route has any source-based access control at all — both are intentionally, fully public.

## Solution

Introduce a small, host-networked TCP relay dedicated to the tailnet-facing access path, which preserves the real client IP across the masquerade boundary using the PROXY protocol. Public-facing traffic (the VPS's public IP, and anything Cloudflare-proxied) is completely untouched: it keeps reaching Caddy exactly as it does today, on the same published ports, with no PROXY protocol involved at any point.

Caddy does **not** terminate PROXY protocol out of the box — `caddy.listeners.proxy_protocol` is a non-standard module that must be compiled in via `xcaddy`, the same build mechanism epic 19 introduced (`roles/gateway/files/Dockerfile`) to add the Cloudflare DNS plugin. This epic adds a second `--with` module to that same Dockerfile; it does not introduce a new build mechanism.

Concretely, for the ports that carry source-IP-gated routes (80 and 443 — matrix/owntracks' port 8443 is untouched, see Out of Scope):

1. Caddy's own port-publish narrows from "all interfaces" to the VPS's **public** IP specifically, freeing the same port number on the VPS's **Tailscale** IP(s).
2. A new relay component, run with host networking (mirroring the existing precedent of `beszel-agent`'s own `network_mode: host` for a different reason), binds to the VPS's Tailscale IP — **both the v4 (`100.64.0.0/10`) and v6 (`fd7a:115c:a1e0::/48`) tailnet addresses**, matching this repo's existing dual-stack treatment of Tailscale access elsewhere (epic 18's DOCKER-USER v6 rules already handle both address families for the same `tailscale_subnet`/`tailscale_subnet_v6` pair; this epic doesn't introduce a v4-only gap into that otherwise-consistent picture) — on those same port numbers. It accepts the raw TCP connection, prepends a PROXY protocol header carrying the real (now-still-real, since the relay sits *before* Tailscale's masquerade point relative to the docker bridge) source IP, and forwards the connection into Caddy.
3. Caddy gains a second, **internal-only** listener (bound to loopback, never published beyond the host) that trusts and unwraps PROXY protocol — reachable only by the new relay, never by the public internet. Caddy's existing public-facing listener is completely unchanged: no PROXY protocol wrapper, no new trust surface, so nothing about already-correct public-facing behavior is touched.
4. **Correction to an earlier draft of this spec**: `mfa_auth`/`tailnet_only`'s matchers (`not remote_ip {{ tailscale_subnet }}`) check only the v4 tailnet range today — `tailscale_subnet_v6` is defined in `group_vars/all/main.yml` and used by the DOCKER-USER v6 firewall rules, but was never wired into either Caddyfile matcher. Left as-is, a v6-connecting tailnet client would still be misclassified as "not tailscale" even after the relay/listener fix above — the masquerade bug would be fixed, but the pre-existing v4-only matcher gap would silently take its place for v6 clients. This epic extends both matchers to `not remote_ip {{ tailscale_subnet }} {{ tailscale_subnet_v6 }}` (Caddy's `remote_ip` matcher accepts multiple ranges natively) — a one-line, additive extension of the existing check, not a redesign of either mechanism's logic or the gateway route schema.

This is a targeted fix at the network layer plus one small matcher correction, not a redesign of either access-control mechanism: the schema and every route's field values are unaffected, and `mfa_auth`/`tailnet_only`'s own structure changes only by the one-line v6 addition in point 4.

## User Stories

1. As a VPS operator, I want `monitor.<domain>` (and any other `tailnet_only` route) to actually load when I connect to it over Tailscale, so that the hostname-based access this repo already documents as the primary path actually works.
2. As a VPS operator, I want `wiki.<domain>`/`dash.<domain>` to correctly skip the Authelia MFA challenge when I'm connecting over Tailscale, matching ADR-0001's stated intent, so that the "VPN already authenticates me" convenience is real, not theoretical.
3. As a security reviewer, I want the fix to be scoped to exactly the tailnet-facing path, so that public-internet and Cloudflare-proxied traffic's existing, already-correct access control is provably untouched by this change.
4. As a security reviewer, I want Caddy's PROXY-protocol-trusting listener to be reachable *only* by the new relay (bound to loopback, never published to the internet or the Docker bridge's public-reachable side), so that nobody on the public internet can forge a PROXY protocol header to spoof a Tailscale-range source IP and bypass MFA or a `tailnet_only` hard-block.
5. As a maintainer, I want the relay to run with host networking (like `beszel-agent` already does, for its own reason), so that it can bind directly to the VPS's Tailscale interface IP the same way Tailscale's own daemon does.
6. As a maintainer, I want Caddy's public-facing listener and the new internal-only listener to be provably distinct — the public one never gets a `listener_wrappers`/PROXY-protocol config, so a future edit can't accidentally merge them and reopen the spoofing risk in user story 4.
7. As a maintainer, I want this fix scoped to exactly the ports that carry source-IP-gated routes (80 and 443 today), not applied blanket to every Caddy listener, so port 8443 (matrix/owntracks, epic 19 — no source-based gating at all) is untouched and doesn't grow an unnecessary PROXY-protocol dependency.
8. As a maintainer, I want each service's own raw published port (Beszel's 8090, AdGuard's 3001) explicitly confirmed and documented as unaffected by this bug (they have no source-IP gate to begin with), so nobody mistakenly "fixes" something that was never broken there.
9. As a maintainer, I want matrix/owntracks (port 8443) explicitly confirmed and documented as unaffected — no source-based access control exists on either route — so this epic's scope stays visibly bounded to the two mechanisms it actually touches.
10. As a future reviewer, I want the root cause (Tailscale's own local-subnet masquerade, not a Docker or Caddyfile bug) documented clearly, so nobody re-diagnoses this from scratch or mistakes it for a `DOCKER-USER` firewall gap.
11. As a VPS operator, I want the actual fix verified against the real VPS (real Tailscale client, real masquerade behavior, real PROXY protocol handshake) before this ticket is considered done, in this repo's established style for anything requiring live external/network state (epic 18's DNS handover, epic 19's DNS-01 issuance) — a pure Ansible-render test cannot prove this class of bug is fixed.
12. As a maintainer, I want this epic to leave `mfa_auth`'s and `tailnet_only`'s matcher names, structure, and the gateway route schema unchanged — aside from the one-line `tailscale_subnet_v6` addition needed to close the pre-existing v4-only gap this investigation surfaced — so this reads as a targeted fix, not a redesign of either access-control mechanism.
13. As a VPS operator connecting from a v6-only or dual-stack Tailscale client, I want the same fix applied for my connection as for a v4 client, so that the relay and the matcher extension don't silently leave IPv6 tailnet access broken while fixing it for v4 — matching this repo's existing dual-stack treatment of Tailscale access everywhere else (the DOCKER-USER v6 firewall rules already handle both address families for the same subnet pair).

## Implementation Decisions

- **Scope**: ports 80 and 443 only — the two ports that carry `mfa_auth`- or `tailnet_only`-gated routes today (every route in `gateway_routes` other than `matrix`/`owntracks` renders on the default port, i.e. 443, confirmed by grepping every role's `gateway_publish` default for an explicit `port:` field). Port 8443 (matrix/owntracks) is untouched — no source-IP gate exists on either of those routes.
- **New relay component**: a small, purpose-built TCP relay (HAProxy in TCP mode, using its `send-proxy`/`send-proxy-v2` backend directive, is the natural fit — a general-purpose, well-documented tool for exactly "accept a raw TCP connection, forward it elsewhere with a PROXY protocol header prepended"; the exact tool is a ticket-level implementation detail, not fixed here). Runs with `network_mode: host` so it can bind directly to the VPS's Tailscale interface IP, mirroring the `beszel-agent` precedent for the same networking mode (different underlying reason: that one needs host-level network-interface stats, this one needs to bind a specific host interface's IP — both need to escape the Docker bridge to reach something host-level).
- **Caddy's public port-publish narrows to the VPS's public IP specifically** (not the current all-interfaces bind), freeing the same port numbers on the Tailscale interface's IP for the new relay to claim exclusively.
- **Caddy gains a second, internal-only listener** bound to loopback (never published to the Docker bridge's externally-reachable side or the public internet), configured to trust and terminate PROXY protocol — reachable only by the new relay. The existing public-facing listener keeps its current configuration exactly as-is: no PROXY protocol trust, no change to its `trusted_proxies` setting.
- **No changes to the gateway route schema or any route's field values, and no redesign of `mfa_auth`/`tailnet_only`'s logic** — the one exception is extending both matchers' `not remote_ip` clause to also check `tailscale_subnet_v6` (see Solution, point 4), a one-line additive fix for a pre-existing v4-only gap this investigation surfaced, not a change to either mechanism's design.
- **How the two required IP addresses are obtained at deploy time is unresolved and must be decided by whichever ticket implements this** — no existing variable holds either. The design needs (a) the VPS's public IP, to narrow Caddy's port-publish, and (b) the VPS's own Tailscale IP(s) (v4 and v6), for the relay to bind to. Candidates to evaluate: Ansible's own gathered facts (`ansible_default_ipv4.address` for the public IP; `ansible_tailscale0.ipv4.address`/`ansible_tailscale0.ipv6` for the Tailscale IPs, since `tailscale0` is a real interface Ansible's `setup` module already sees once Tailscale is up) versus a manually-set `group_vars` value versus parsing `tailscale ip`/`tailscale status --json` output directly. Whichever is chosen must work reliably during a `--check` run and not assume Tailscale is already up when Ansible's facts are gathered (`tailscale0` doesn't exist as an interface until the `tailscale` role's own "bring up Tailscale" task has already run in the same play — an ordering constraint the implementing ticket must account for).
- **PROXY-protocol trust is a hard security boundary**: the internal listener must never be reachable from anywhere except the relay's own loopback-bound connection. Getting this wrong (e.g., accidentally publishing the internal listener, or applying the PROXY-protocol wrapper to the public listener) would let anyone on the public internet forge a PROXY header claiming a `100.64.0.0/10` source and fully bypass both `mfa_auth` and `tailnet_only` — this is treated as a security-critical implementation detail, not a minor config nit.
- **Each service's own raw published port (Beszel 8090, AdGuard 3001) needs no change** — they have no source-IP gate of their own, so the masquerade doesn't affect them; they're already correctly reachable over Tailscale today, and this epic doesn't touch them.

## Testing Decisions

- **What makes a good test**: as with epic 18's DNS handover and epic 19's DNS-01 issuance, the *live* behavior this epic fixes (a real Tailscale client's traffic actually surviving the masquerade round-trip and reaching Caddy with its real IP intact) cannot be exercised by a pure Ansible-render or `docker compose config` test — there is no Tailscale network, no real masquerade behavior, and no real PROXY protocol handshake available in a rendering-only test environment. That verification is operator-validated on the real VPS, per this repo's established practice for anything requiring live external/network state.
- **What CAN be tested statically**, and should be:
  - `roles/gateway/files/Dockerfile` builds with the PROXY-protocol module compiled in alongside the existing Cloudflare DNS plugin — mirroring epic 19 ticket #01's own "does the binary actually have the module" verification (`list-modules` output), not just that the Dockerfile *text* mentions a second `--with` flag.
  - The new relay's compose fragment uses `network_mode: host` and binds to the expected port(s) — a render-level assertion, same shape as existing compose-fragment tests.
  - Caddy's compose fragment's public port-publish is scoped to a specific IP, not `0.0.0.0`/unscoped — a regression guard proving the "narrow the public bind" decision actually landed, not just intended.
  - The rendered Caddyfile's internal PROXY-protocol-trusting listener is bound to loopback only, and — the security-critical assertion — the *public-facing* listener's config does **not** carry a PROXY-protocol wrapper. This is the single most important regression guard this epic adds: it directly protects against the MFA/tailnet_only bypass risk called out in the Implementation Decisions above, and should be written the same way this repo's other "prove the dangerous case can't happen" tests are (e.g., epic 19's `dns cloudflare` occurrence-count assertion, epic 18's tailnet_only-vs-mfa_auth matcher-name distinctness).
  - Both `mfa_auth`'s and `tailnet_only`'s `not remote_ip` matchers include `tailscale_subnet_v6` alongside the existing v4 constant — a regression guard for the pre-existing gap this investigation surfaced, verified by rendering with both group_vars present and asserting both appear in the matcher line.
  - Every existing gateway-render assertion (matrix/owntracks byte-exact blocks, tailnet_only/mfa_auth route counts, etc.) continues to pass unchanged — proving this epic doesn't alter any existing route's rendered output beyond the matcher extension above.
- **Prior art**: mirror `tests/check-adguard-dns.sh`'s framing (a STATIC-only guard with an explicit comment explaining why the live behavior itself is operator-validated, not asserted in CI) for the overall shape of this epic's test script; mirror `tests/test_gateway_render.yml`'s existing byte-exact/count-assertion style for the Caddyfile-level checks.

## Out of Scope

- **Matrix/OwnTracks (port 8443, epic 19)** — no source-based access control exists on either route today; this epic doesn't add one and doesn't touch port 8443 at all.
- **Each service's own raw published port** (Beszel's 8090, AdGuard's 3001) — confirmed unaffected (no source-IP gate to break), left completely alone.
- **Re-architecting Caddy to run in host network mode.** Considered and explicitly rejected in favor of the PROXY-protocol relay: host networking would fix the same underlying problem, but at the cost of Caddy losing Docker's embedded DNS resolution for every backend it proxies to (`reverse_proxy conduit:8008` and friends) — every `reverse_proxy` target across every route would need re-plumbing to a stable published-port or static-IP address instead of a service name. The relay approach fixes the same problem with a single small new component and zero changes to any existing `reverse_proxy` target.
- **Any change to `mfa_auth`'s or `tailnet_only`'s matcher names, structure, or the gateway route schema** beyond the one-line `tailscale_subnet_v6` addition (Solution, point 4) — this epic is a network-layer fix underneath those mechanisms plus one small pre-existing-gap correction it surfaced, not a redesign of either.
- **Disabling or reconfiguring Tailscale's own masquerade behavior** (e.g., investigating `tailscale set` flags) — not pursued: it's not a documented, supported knob for this specific "peer reaches this host's own service" case (as opposed to subnet-router route masquerading, which does have a flag), and even if one existed, relying on undocumented Tailscale internals would be more fragile than a self-contained relay this repo fully controls.
- **Fixing this for any route the operator might add in the future that also needs source-based gating** — this epic fixes the mechanism for the two access-control types that exist today (`mfa_auth`, `tailnet_only`); a hypothetical future third mechanism is out of scope until it actually exists.

## Further Notes

- The bug's blast radius took real, empirical work to establish (not assumed): confirmed via the VPS's actual `iptables -t nat -L ts-postrouting` output, a real Caddy access-log `remote_ip` capture, and cross-checking every affected route's actual public DNS record (several routes turned out to already be Cloudflare-proxied, which sidesteps the bug for THAT specific access path but doesn't fix tailnet-facing access — those are two independent paths to the same hostname).
- `owntracks-ui.<domain>` was found, during this investigation, to have a public/Cloudflare-proxied DNS record despite being a `tailnet_only` route — which (independently of this epic's bug) makes it currently unreachable by anyone via that hostname at all, since Cloudflare's edge IP never matches `tailscale_subnet` either. Whether that DNS record should exist at all is an operator/DNS-console question, not something this epic's code touches — flagging it here so it isn't lost, not folding it into this epic's scope.
- This epic's fix, once live, should be spot-checked against every currently-affected route (`monitor`, `owntracks-ui`, `adguard`, `wiki`, `dash`) over a real Tailscale connection — not just `monitor`, which is merely the one that surfaced the bug first.
