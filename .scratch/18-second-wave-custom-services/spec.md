# Spec: Second Wave of Custom Docker Services (OwnTracks Frontend, Beszel, AdGuard Home)

> Status: ready-for-agent (no longer draft — all grill/me decisions captured, pattern re-verified against epics 12/13/15)
> Source: Epic 18 — "add three new services to the stack"
> Related: `12-add-custom-services` (the origin of the custom-service pattern this epic reapplies three more times), `13-gateway-route-schema` (the `gateway_routes` schema/validation this epic extends with one new field — see below; the schema/validation *engine* itself is unchanged, exactly the kind of routine growth epic 13 designed the schema to absorb), `15-role-ordering-check` (the "new role becomes a `gateway` meta dependency, not a fresh `site.yml` entry" precedent this epic follows for `beszel` and `adguard`), `17-docker-single-execution` (documents that `docker`/`wiki_volume` already run more than once per deploy; this epic adds two more `wiki_volume`-dependent roles, which is expected to move those counts, not regress them below the epic-17 ceiling — see Testing Decisions)
> Vocabulary: "OwnTracks frontend", "OwnTracks recorder" (existing), "Beszel hub", "Beszel agent", "PocketBase superuser", "AdGuard Home", "systemd-resolved stub listener", "global override nameserver" (Tailscale DNS), "restricted port class", "gateway_publish", "docker_published_restricted_ports", "source-based MFA bypass" (existing model, ADR-0001: public + Authelia-challenge-unless-Tailscale), "tailnet-only route" (new model this epic introduces: hard-blocked for non-Tailscale sources, no public path exists at all)

## Problem Statement

The VPS runs a fixed set of services provisioned via epics 1–17. Epic 12 established a repeatable pattern for adding a custom Docker service (service fragment + `gateway_publish` contribution or UFW rule + secrets manifest entry), demonstrated with OwnTracks and Syncplay. The user wants to exercise that pattern three more times, each with a genuinely different shape than what's been built so far:

1. **A web UI for OwnTracks.** The existing `owntracks` role (epic 12) deployed only the Recorder — an HTTP API with no browser-facing UI. Checking location history today means querying the API by hand.
2. **Local server monitoring.** There is no visibility into the VPS's own health (CPU, memory, disk, container status) beyond SSHing in and running commands manually.
3. **Self-hosted DNS + ad-blocking.** DNS resolution for the operator's Tailscale-connected devices currently goes wherever each device's OS/network defaults it — no ad/tracker blocking, no visibility into what's being resolved.

Each of these three services introduces a new wrinkle the existing pattern hasn't had to handle yet: a component with **no auth of its own** sitting behind a data-exposing route (OwnTracks frontend), a **two-container producer/consumer pair with an externally-issued credential** that can't be pre-seeded by Ansible the way every other secret in this repo is (Beszel hub+agent), and a service that needs a **host-level, potentially disruptive config change** (freeing port 53 from systemd-resolved) plus **two conflicting default ports** to reconcile against services already running (AdGuard Home vs. SilverBullet's 3000).

**A fourth wrinkle surfaced during the spec's own review, worth stating plainly because it corrects an error in this document's first draft**: this repo's only existing "private" route model (ADR-0001's source-based MFA, used by `wiki`/`dash`/`auth`/`matrix`) is not actually Tailscale-only. Those routes are reachable from the public internet on port 443; Caddy challenges non-Tailscale sources with Authelia and lets Tailscale sources bypass the challenge (they're already VPN-authenticated). That's a deliberate, sensible tradeoff for a wiki — but this epic has three surfaces (OwnTracks's location-history viewer, Beszel's hub, AdGuard's admin UI) that should have **no public path at all**, not just an MFA-gated one. That model doesn't exist in this repo yet — the gap is part of what this epic needs to close, via one small, additive schema field rather than by reaching for the existing `mfa` field and getting the exposure wrong.

## Solution

Add three services, each slotting into the existing seams (docker service fragment, `gateway_publish` contribution, tailscale-role-owned firewall, single secrets manifest). This requires exactly **one small, additive change to the gateway route schema** (epic 13): a new `tailnet_only` boolean field, which renders a hard Caddy-level block (respond with 404, no forward_auth involved) for any source outside the Tailscale subnet — genuinely no public path, as opposed to `mfa: true`'s "public, but challenged unless Tailscale." This is exactly the shape of growth epic 13's schema/validation engine was built to absorb (one schema-table row, one `{% if %}` block in `Caddyfile.j2`), not a redesign of it.

- **OwnTracks frontend**: a second gateway route (`owntracks-ui.<domain>`) added to the existing `owntracks` role's `owntracks_gateway_publish` list, pointing at a new frontend container that reverse-proxies its own `/api`/`/ws` calls to the recorder over the internal `gateway` docker network. The existing `owntracks.<domain>` → recorder route (mobile app's ingest endpoint, `/pub`) is **completely untouched** — public HTTPS, basic-auth only, no MFA — and remains the *only* piece of OwnTracks exposed to the public internet, per explicit instruction. The new frontend route uses `tailnet_only: true` (no public path, no MFA needed — Tailscale device auth alone is trusted, consistent with the rest of this stack's trust model) and needs no new secret.
- **Beszel**: a new `beszel` role running the hub (web UI + SQLite-backed PocketBase store) and a local agent monitoring the VPS itself over a shared Unix socket (no docker.sock mount, no network hop). The hub gets a `tailnet_only: true` gateway route — no public path, no MFA. The agent's connection credential (a key/token pair the hub *generates itself* after first boot) is handled as an operator-supplied secret populated *after* a first partial deploy — the same shape as this repo's existing `tailscale_authkey` (a secret obtained from a running system's own UI/console, not something Ansible can originate).
- **AdGuard Home**: a new `adguard` role. The web UI is pre-seeded via a mounted config file (bcrypt password hash, same shape as the existing Authelia/dashboard admin-password-hash secrets) so the interactive setup wizard never runs; it gets a `tailnet_only: true` gateway route on a port that doesn't collide with SilverBullet's 3000. DNS (port 53, UDP+TCP) is published but restricted to the Tailscale subnet at the firewall (the same `docker_published_restricted_ports` mechanism as every other Tailscale-only-at-the-network-layer service, extended to also cover UDP). The role frees port 53 on the host by disabling systemd-resolved's stub listener, sequenced so the host never loses DNS resolution mid-change. Making AdGuard the tailnet's actual resolver (a Tailscale admin-console "override DNS" setting) is a documented manual step, not Ansible-automatable — the same category as the operator having to obtain `TAILSCALE_AUTHKEY` from that same console today.

## User Stories

### Gateway route schema: the new `tailnet_only` model

1. As a security reviewer, I want a route type that's hard-blocked (404) for any source outside the Tailscale subnet, not just challenged with MFA, so that genuinely private services (location history, monitoring, DNS admin) have zero public attack surface — not "public but gated."
2. As a VPS operator, I want `tailnet_only` to require no MFA for Tailscale-connected devices, so that reaching my own private dashboards from my own authorized devices doesn't add a redundant login step on top of the VPN authentication I already did — consistent with how every existing Tailscale-bypass route in this stack already treats Tailscale membership as sufficient.
3. As a maintainer, I want `tailnet_only` added as one new row in the existing route schema table (`roles/gateway/vars/main.yml`) and one new `{% if %}` block in `Caddyfile.j2`, so that adding it follows exactly the shape epic 13 predicted for future fields — not a special case, not a reason to reopen epic 13's design.
4. As a test author, I want `validate.yml`'s generic per-field engine to enforce `tailnet_only`'s type (boolean) automatically once it's declared in the schema, so that a malformed value fails fast the same way every other field already does, with no new hand-written assert needed.
5. As a reviewer, I want every existing route (`wiki`, `dash`, `auth`, `matrix`, the OwnTracks recorder, `syncplay`) to render byte-identical Caddyfile output after this change, so that adding a new field to the schema is provably additive, not a behavior change to what's already deployed.

### OwnTracks frontend

6. As a VPS operator, I want a browser-based UI for my OwnTracks location history, so that I don't have to query the Recorder's HTTP API by hand to see where I've been.
7. As a VPS operator, I want the OwnTracks frontend served at its own host (`owntracks-ui.<domain>`), so that adding it doesn't disturb the mobile app's existing, already-configured endpoint (`owntracks.<domain>`).
8. As a mobile OwnTracks app user, I want my app's configured server URL and its basic-auth requirement to keep working completely unchanged after this epic ships, so that I don't have to reconfigure location reporting on my phone.
9. As a VPS operator, I want the frontend to reach the Recorder over the internal Docker network (not through another public hop), so that browser-to-API calls aren't an unnecessary extra round trip through Caddy.
10. As a security reviewer, I want the new `owntracks-ui` route to be `tailnet_only` (hard-blocked for non-Tailscale sources), so that a UI with no login of its own — viewing my most sensitive personal data, my location history — has no public path at all, not merely an MFA-gated one.
11. As a VPS operator, I want only the original recorder's `/pub` ingest exposed to the public internet with basic-auth, and nothing else related to OwnTracks reachable publicly, so that adding a browser UI doesn't widen OwnTracks's public attack surface in any way.
12. As a maintainer, I want the new route added within the existing `owntracks` role (not a new role), so that OwnTracks-related config stays in one place.

### Beszel (local monitoring)

13. As a VPS operator, I want a dashboard showing the VPS's own CPU, memory, disk, and container health, so that I have visibility without SSHing in and running commands by hand.
14. As a VPS operator, I want the Beszel hub's web UI to be `tailnet_only` (no public path), so that a dashboard revealing my VPS's full operational profile is never reachable from the public internet, not even behind an MFA challenge.
15. As a VPS operator, I want the Beszel agent to monitor the same VPS the hub runs on via a local connection (not a published network port), so that "local monitoring" doesn't require opening any new network surface for the agent.
16. As a security reviewer, I want the Beszel agent to avoid mounting the Docker socket, so that its privilege stays minimal — host-level stats are enough for an "is the VPS healthy" dashboard; container-level detail isn't worth the added access.
17. As a VPS operator, I want the hub's persistent data (its SQLite-backed store) to survive container restarts, so that historical monitoring data isn't lost on every redeploy.
18. As a VPS operator, I want the one-time step of pairing the agent to the hub (obtaining the hub-generated key/token and feeding it back into the agent's config) documented clearly, so that I know this is a manual/two-pass step and not something a single playbook run completes end to end — the same shape as obtaining `TAILSCALE_AUTHKEY` from the Tailscale console today.
19. As a future epic author, I want it recorded that Beszel's hub-generated agent credential can't be pre-seeded through the secrets manifest the way every other secret in this repo is, so that a future attempt to "just add it to `.env` like everything else" doesn't get stuck rediscovering this constraint.
20. As a maintainer, I want the hub and agent to each have their own service fragment (mirroring how every other service in `docker_enabled_services` is one fragment = one container), so the consolidated compose file's structure stays consistent.

### AdGuard Home (DNS + ad-blocking)

21. As a VPS operator, I want AdGuard Home to actually serve DNS for my Tailscale-connected devices, so that ad/tracker blocking is real (applies to all their traffic), not just a dashboard that isn't in the resolution path.
22. As a VPS operator, I want AdGuard's admin UI to be `tailnet_only` (no public path), so that DNS configuration and query-log visibility — which reveals every domain every device on my tailnet resolves — is never reachable from the public internet, not even behind an MFA challenge.
23. As a VPS operator, I want AdGuard's admin UI on a port that doesn't collide with SilverBullet's existing published port 3000, so that both services can run simultaneously without a port conflict.
24. As a VPS operator, I want AdGuard's initial admin account and core config pre-seeded before first boot, so that deploying it doesn't require a manual browser-based setup wizard step that Ansible can't drive.
25. As a security reviewer, I want AdGuard's admin password stored as a bcrypt hash in the secrets manifest (like the existing Authelia/dashboard admin secrets), so that no plaintext admin password is ever written to disk or version control.
26. As a VPS operator, I want DNS (port 53, UDP and TCP) reachable only from Tailscale clients, not the public internet, so that the resolver isn't an open DNS relay for the whole internet.
27. As a VPS operator, I want the host's own DNS resolution (systemd-resolved) to keep working throughout the change that frees port 53 for AdGuard, so that the VPS itself doesn't lose name resolution mid-deploy.
28. As a security reviewer, I want the systemd-resolved stub-listener change sequenced so port 53 is never simultaneously unbound on the host and unbound in the AdGuard container, so that there's no window where DNS resolution fails for everything.
29. As a VPS operator, I want it documented that pointing my Tailscale devices at AdGuard (the tailnet-wide "override DNS servers" setting) is a manual step in the Tailscale admin console, so that I know Ansible can prepare the resolver but can't flip that tailnet-wide switch itself.
30. As a future epic author, I want it recorded that Tailscale's relevant DNS feature for this use case is the *global override nameserver* setting, not split-DNS (which solves a different problem — routing specific domains elsewhere), so a future revisit doesn't waste time investigating the wrong mechanism.
31. As a maintainer, I want AdGuard's config/data directories bootstrapped the same way OwnTracks's storage directory is (a host bind-mount owned by the `llm_wiki` uid via the `wiki_volume` module, not a Docker-initialized named volume), so that the non-root container doesn't fail to write on first boot the way OwnTracks's recorder originally did.

### Shared / pattern

32. As a VPS operator, I want all three services to appear in the consolidated `docker-compose.yml`, so the full service inventory stays auditable in one file.
33. As a maintainer, I want `beszel` and `adguard` (the two new roles with a `gateway_publish` contribution) to become dependencies of the `gateway` role via `meta/main.yml`, not fresh explicit `site.yml roles:` entries, so that they don't reintroduce the double-execution bug epic 15 already found and fixed for `owntracks`.
34. As a maintainer, I want it explicit that this epic deliberately introduces exactly one new access model (`tailnet_only`) on top of the three that already existed (source-based-MFA-bypass; public HTTPS+basic-auth; IP-restricted raw TCP+password), so that the addition reads as a considered, minimal extension — not scope creep, and not something to repeat casually for a fifth model without equally clear justification.
35. As a VPS operator, I want each new role's tasks tagged and listed in the skip-tags guard (epic 10) and the README's skippable-roles table, so that `--skip-tags beszel` / `--skip-tags adguard` works like every other role.
36. As a reviewer, I want this epic to touch zero existing routes' rendered output (`wiki`, `dash`, `auth`, `matrix`, the OwnTracks recorder, `syncplay`) beyond adding new ones alongside them, so existing services' access posture is provably unchanged.

## Implementation Decisions

### Gateway route schema addition: `tailnet_only`

- **New schema field** in `roles/gateway/vars/main.yml` (epic 13's route schema table): `tailnet_only`, `required: false`, `type: boolean`. Enforced automatically by `validate.yml`'s existing generic per-field engine — no new hand-written assert needed, exactly as epic 13 designed.
- **New `Caddyfile.j2` snippet**, parallel in structure to the existing `mfa_auth` snippet but with a hard response instead of a challenge:
  ```jinja2
  (tailnet_only) {
    @not_tailscale not remote_ip {{ tailscale_subnet }}
    respond @not_tailscale 404
  }
  ```
  and, in the per-route block, `{% if route.tailnet_only %}  import tailnet_only{% endif %}` alongside the existing `{% if route.mfa %}` block. A route may in principle set both `tailnet_only` and `mfa` — harmless (the MFA challenge would only ever apply to traffic that `tailnet_only` already blocked), not worth a mutual-exclusivity constraint for one theoretical case, consistent with epic 13's stance on not over-generalizing for a single instance.
- **This is the entirety of the schema-side change.** No other existing field, route, or role's `gateway_publish` contribution is touched. `wiki`, `dash`, `auth`, `matrix`, the OwnTracks recorder, and `syncplay` (UFW-only, no gateway route) are all unaffected.

### OwnTracks frontend

- **No new role.** The existing `owntracks` role gains a second service fragment (`owntracks/frontend` image) and a second entry appended to its existing `owntracks_gateway_publish` list — `host: owntracks-ui`, `upstream: <frontend container>:80` (the image's default listen port), `tailnet_only: true`, `mfa: false` (Tailscale device auth alone is trusted; no double-gate — see Further Notes). This is deliberately the *opposite* access posture from the existing recorder entry (`mfa: false`, `tailnet_only` absent/false, public, `tls_mode: auto`, `basic_auth_user`/`hash`, shared `:8448`) — only the recorder stays public; the frontend has no public path and needs no basic-auth secret at all.
- **Frontend configured via env vars** pointing at the recorder's docker-network service name/port — confirmed to be the image's supported mechanism (no mounted `config.js` required).
- **Recorder's `/pub` endpoint (mobile app ingest) is untouched** — confirmed the frontend image proxies only `/api`/`/ws` to the recorder, never `/pub`, so the recorder must keep its own public route rather than the frontend becoming a single merged upstream for both concerns.
- **No `path`-based routing needed.** Two independent host-based routes with two different access-model shapes; the schema's only addition here is the boolean field above.

### Beszel

- **New role**: `roles/beszel`, depending on `wiki_volume` (directory bootstrap for the hub's data dir and the shared agent-socket dir), same shape as `roles/owntracks/meta/main.yml`.
- **Two service fragments**: `beszel-hub` (web UI, port 8090 internally) and `beszel-agent` (no published port — connects to the hub over a shared Unix socket, bind-mounted host directory shared between the two containers, not a Docker named volume, matching the rest of this repo's bind-mount-over-named-volume convention for non-root-writable data).
- **Hub gateway route**: `tailnet_only: true`, `mfa: false` — no public path, no MFA. Hub's own container port (8090) is also published directly and added to the `docker_published_restricted_ports` firewall class, mirroring how SilverBullet's 3000 is both Caddy-routed *and* firewall-restricted as belt-and-suspenders — this is an independent enforcement layer from the Caddy-level `tailnet_only` block (a raw-port connection never goes through Caddy at all).
- **Hub persistent storage**: a host bind-mount directory (owned by `llm_wiki`, bootstrapped via `wiki_volume`'s `ensure_directory` entrypoint — the same pattern `owntracks` already uses for its storage dir) for the PocketBase data directory.
- **Agent has no docker.sock mount** — host-level stats only (CPU/memory/disk/network), per the grilled decision to keep its privilege minimal. Container-level stats are out of scope (see Out of Scope).
- **Agent↔hub pairing is a documented manual/two-pass step, not a single-run Ansible flow**: the hub generates its own ed25519 keypair and, when the operator adds a "system" via its web UI, surfaces a key+token pair for that system. This pair is captured as two new secrets-manifest entries (`beszel_agent_key`, `beszel_agent_token`) that the operator populates in `.env` *after* a first deploy that brings up the hub alone — structurally identical to how `TAILSCALE_AUTHKEY` is obtained from an external console today, not a new category of exception to the secrets-manifest pattern.
- **Hub's own admin-account bootstrap mechanism (whether its PocketBase superuser account can be pre-seeded non-interactively, or requires the same kind of first-run manual step as the agent pairing) is UNVERIFIED and must be confirmed by whichever ticket implements the hub**, the same way epic 12 flagged the Syncplay image's config mechanism as unverified before implementation. If it can't be pre-seeded, document it as a manual first-boot step alongside the agent pairing.

### AdGuard Home

- **New role**: `roles/adguard`, depending on `wiki_volume` (directory bootstrap for its config and data directories, owned by `llm_wiki`).
- **Config pre-seeding**: the role renders an `AdGuardHome.yaml` (bcrypt admin password hash from `secrets.adguard_admin_password_hash`, username from `secrets.adguard_admin_username` with a default, DNS bind on all interfaces port 53, HTTP admin listen on an internal port that does not collide with SilverBullet's 3000) and bind-mounts it before first container start, so the interactive setup wizard never runs.
- **New secrets-manifest entries**: `adguard_admin_username` (optional, default `"admin"`, same shape as `silverbullet_admin_username`/`authelia_admin_username`), `adguard_admin_password_hash` (required, no default — precomputed bcrypt hash, same shape as `authelia_admin_password_hash`/`hermes_default_dashboard_admin_password_hash`).
- **Admin UI gateway route**: `tailnet_only: true`, `mfa: false` — no public path, no MFA. The container's admin-UI port is also published directly and added to `docker_published_restricted_ports`, same belt-and-suspenders reasoning as Beszel's hub.
- **DNS port (53, UDP+TCP) is Tailscale-only, not public.** This requires extending the tailscale role's firewall mechanism: today's `docker_published_restricted_ports` / DOCKER-USER restricted-port rules are TCP-only. A parallel restricted-port class for UDP (new list, e.g. alongside `docker_published_restricted_ports`) is added, with the equivalent DOCKER-USER v4/v6 accept/deny rules mirrored for `protocol: udp`. Port 53 also needs the existing TCP restricted-port treatment (some DNS traffic, e.g. TCP fallback for large responses, uses TCP too) — so 53 is added to *both* the existing TCP restricted-port list and the new UDP one.
- **Host-level systemd-resolved change, owned by the `adguard` role** (not `common` or `tailscale`) — the role that needs port 53 free is responsible for freeing it, matching the existing convention of `owntracks` installing its own `passlib` dependency rather than pushing it into `common`. Disables the stub listener via a drop-in config file (not editing the shipped `resolved.conf` directly) and reloads the service. **Sequencing is load-bearing**: the AdGuard container must already be bound to port 53 (or the change applied atomically with the container start) before the host's own resolver stops listening there, so the host is never left with no working DNS resolution mid-deploy. This role's tasks run in the normal config-deploying phase, before the epic-16 end-of-play "start consolidated docker compose stack" step — matching how every other config-rendering role is already sequenced ahead of that step.
- **Tailnet-wide DNS override (Tailscale admin console "override DNS servers" pointed at AdGuard's Tailscale IP) is a documented manual step**, not Ansible-automated — it is a change to Tailscale's own hosted admin console, the same category of manual, external-console step as generating `TAILSCALE_AUTHKEY` itself.
- **No `network_mode: host`** — confirmed bridge networking with explicit `-p 53:53/udp -p 53:53/tcp` port publishing (plus the admin-UI port) works for this scope; host networking is only needed for AdGuard's DHCP-server feature, which is out of scope.

### Shared

- **`beszel` and `adguard` become `gateway` meta dependencies**, not fresh `site.yml roles:` entries — the same fix epic 15 ticket #01 already applied for `owntracks`, avoiding reintroducing double execution for either new role.
- **`docker_enabled_services`** gains `owntracks-frontend`, `beszel-hub`, `beszel-agent`, `adguard`. **No new named volumes** — all new persistent/shared state uses host bind-mounts owned by `llm_wiki`, consistent with why `owntracks_data_dir` is a bind mount rather than a Docker named volume.
- **Skip-tags guard (epic 10)**: `beszel` and `adguard` each get task-level `tags: [<role>]` on every task, and are added to `tests/lint.sh`'s role-tag-guard loop and the README's skippable-roles table.
- **Four access models now exist**: source-based-MFA-bypass (public + Authelia-challenge-unless-Tailscale: `wiki`/`dash`/`auth`/`matrix`), public HTTPS+basic-auth (OwnTracks recorder), IP-restricted raw TCP+password (Syncplay), and the new tailnet-only hard-block (OwnTracks frontend, Beszel hub, AdGuard admin UI). Every route in this epic fits the last of these; none introduces a fifth.

## Testing Decisions

- **What makes a good test**: test external behavior — rendered `docker-compose.yml` includes all four new service fragments and passes `docker compose config`; rendered Caddyfile includes `owntracks-ui`, the Beszel-hub route, and the AdGuard route all sharing the `tailnet_only` shape (`import tailnet_only` present, `import mfa_auth` absent, no `basic_auth` block, default TLS/port), while the existing `owntracks` recorder route and `wiki`/`dash`/`auth`/`matrix`/`syncplay` all render byte-identical to their pre-epic output; the tailscale role's firewall tasks reference the new TCP-restricted ports (Beszel hub, AdGuard admin UI) and the new UDP-restricted port class (port 53); the secrets manifest has all new entries; `docker_enabled_services` and the skip-tags guard include the new roles. Don't test Ansible internals or exact iptables rule ordering beyond what existing tailscale tests already assert structurally.
- **Modules tested**:
  - `roles/gateway/vars/main.yml` → declares `tailnet_only` as an 8th schema field (boolean, optional) alongside the existing 7 — catches an accidental deletion of the new entry the same way epic 13's own test protects the original 7.
  - `roles/gateway/tasks/validate.yml` → a schema-violating `tailnet_only` value (non-boolean) fails fast via the same `include_tasks` + `rescue` pattern as the other six type/allowed-values checks — no new hand-written assert needed, proving the generic engine actually absorbed the new field.
  - `roles/gateway/templates/Caddyfile.j2` → renders the `(tailnet_only)` snippet and the per-route `import tailnet_only` for the three new private routes; asserts the existing routes (`wiki`, `dash`, `auth`, `matrix`, OwnTracks recorder) are byte-identical to their pre-epic rendering — proving the addition is additive, not a behavior change.
  - `roles/docker/templates/services/{owntracks-frontend,beszel-hub,beszel-agent,adguard}.yml.j2` → each renders a valid fragment (image, ports/no-ports as appropriate, volumes, networks, env).
  - `roles/owntracks/defaults/main.yml` → `owntracks_gateway_publish` now has two entries with deliberately different access-model shapes: the existing recorder entry keeps `mfa: false`/public/basic-auth unchanged, and the new frontend entry has `tailnet_only: true`, `mfa: false`, and no `basic_auth_user`/`hash` at all — a regression test should fail if the frontend entry ever gains public/basic-auth fields or the recorder entry ever loses them.
  - `roles/beszel/defaults/main.yml`, `roles/adguard/defaults/main.yml` → each role's `*_gateway_publish` entry has the required fields (`host`, `upstream`, `tailnet_only: true`) and passes the schema/validation engine.
  - `roles/tailscale/tasks/main.yml` → new TCP-restricted ports present in the existing list/rules; a new UDP-restricted port class exists with port 53, mirrored DOCKER-USER v4/v6 accept/deny rules matching the existing TCP pattern's structure.
  - `group_vars/all/secrets.yml` → `beszel_agent_key`, `beszel_agent_token`, `adguard_admin_username`, `adguard_admin_password_hash` present with correct `required`/`default` shape.
  - `group_vars/all/main.yml` → `docker_enabled_services` includes all four new services; no new entries in `docker_volumes` (confirms the bind-mount decision held).
  - Consolidated render: `docker compose config` passes with all new services enabled.
  - `setup-env.sh` / `.env.template` — prompts for the new secrets (checked via `scripts/generate-env.py --check`, the existing sync mechanism).
  - Skip-tags guard: `beszel` and `adguard` present in `tests/lint.sh`'s role loop and each role's `tasks/main.yml` has task-level tags.
  - A machine-checked ordering assertion (mirroring `tests/check-role-ordering.sh`) that `beszel` and `adguard` are `gateway` meta dependencies and are **not** also listed as explicit `site.yml roles:` entries — the same double-execution guard epic 15 ticket #01 established for `owntracks`.
- **Prior art**: mirror `tests/test_gateway_render.yml`/`tests/check-gateway-render.sh` (epic 13's own positive/negative-test structure) for the `tailnet_only` schema and render assertions; mirror `tests/check-custom-services.sh` (epic 12) structurally for a new `tests/check-second-wave-services.sh`; mirror `tests/check-role-ordering.sh` for the new dependency-not-explicit-entry assertions; mirror `tests/check-tailscale.sh` for the new UDP-restricted-port-class assertions.

## Out of Scope

- **Beszel monitoring any machine other than this VPS** — single-node scope only; fleet/remote-agent support is a future epic if ever needed.
- **Beszel agent container-level (per-Docker-container) stats** — would require a docker.sock mount; rejected in grilling to keep the agent's privilege minimal. Host-level stats (CPU/mem/disk/network) only.
- **Automating Beszel's agent-pairing key/token retrieval** — this is a hub-generated, UI-surfaced credential; scripting its retrieval via the hub's API is a possible future enhancement, not this epic. The manual step is documented, not eliminated.
- **AdGuard Home's DHCP server feature** — not needed for this epic's DNS+adblock+admin-UI scope; would require `network_mode: host`, which is deliberately avoided here.
- **Automating the Tailscale "override DNS servers" console setting** — Tailscale admin-console-only, no API path pursued in this epic.
- **Path-based Caddy routing / a `path` field in the gateway route schema** — not needed; every new route in this epic is host-based, fitting the existing schema plus the one new `tailnet_only` field.
- **A fifth access model, or requiring MFA in addition to `tailnet_only`** — grilled and explicitly decided against: Tailscale membership alone is sufficient for all three new private routes, consistent with how this stack already trusts Tailscale everywhere else. Revisit only with a concrete new case, not speculatively.
- **Full elimination of `docker`/`wiki_volume` role-execution duplication** — out of scope per epic 17; this epic's two new `wiki_volume`-dependent roles are expected to shift those counts, not required to hold them at epic 17's ceiling (see Testing Decisions' note on updating, not just re-asserting, the epic-17 regression test's bound if the count changes).
- **AdGuard Home HTTPS/DoH/DoT/DNSCrypt listeners** (ports 443/853/QUIC/5443) — plain DNS over 53 (UDP+TCP) only; encrypted-DNS transports are a possible future enhancement.

## Further Notes

- **This spec's first draft mislabeled the existing access model, and the correction is worth keeping visible.** The draft described `wiki`/`dash`/`auth`/`matrix` as "Tailscale-only+MFA" and proposed reusing that same `mfa: true` shape for OwnTracks-ui/Beszel/AdGuard. In fact ADR-0001's model is public-with-MFA-bypass-for-Tailscale, not Tailscale-only — reusing it as originally drafted would have left three deliberately-private surfaces reachable from the public internet, MFA-gated but not actually private. Caught and corrected during the grilling session itself, before any implementation — the fix is the new `tailnet_only` field described above, not a patch to `mfa`'s existing meaning.
- Grilled and settled: `tailnet_only` routes do **not** additionally require MFA for Tailscale-connected devices, even for the OwnTracks frontend (arguably the most sensitive of the three — personal location history). This keeps the trust model uniform with the rest of the stack (Tailscale device auth is treated as sufficient everywhere else) rather than introducing a stricter, one-off posture for a single service.
- **Two components in this epic carry a credential Ansible cannot originate itself**: Beszel's agent key/token (hub-generated, UI-surfaced) and, potentially, Beszel's hub superuser account (mechanism unverified — flagged above for the implementing ticket to confirm). Both are treated as manual/operator-supplied secrets rather than forcing an artificial pre-generation mechanism into the hub role — consistent with how `TAILSCALE_AUTHKEY` already works in this repo.
- **The systemd-resolved change is the highest-risk single step in this epic.** It's a host-level config change with a real failure mode (host loses DNS resolution) if sequenced wrong. The implementing ticket should treat the sequencing constraint (AdGuard bound to 53 before/atomically with the host stub listener going down) as a hard correctness requirement, not a nice-to-have, and should note in its own ticket how it was verified (ideally via a live `--check`/`--diff` or a real deploy, given this repo's established practice — see epics 13, 15, 16, 17 — of catching sequencing bugs that only show up on a live run, not in local tests).
- **Port inventory added by this epic** (for whoever next needs to avoid a collision): Beszel hub admin UI (proposed 8090, matching the image's own default — avoids inventing a new number), AdGuard admin UI (a port distinct from SilverBullet's 3000 — exact number left to the implementing ticket, e.g. 3001, but must be recorded in `group_vars/all/main.yml` next to the other port-class comments), AdGuard DNS (53, both protocols, Tailscale-only).
- **Possible follow-up documentation, not decided here**: the new `tailnet_only` Caddy mechanism reuses the exact same `remote_ip`/`tailscale_subnet` primitive ADR-0001 already documents for the MFA-bypass model, just with a different response (hard block vs. challenge). Worth an ADR addendum or a new small ADR once this ships, per `docs/agents/domain.md`'s lazy-creation guidance — not authored speculatively as part of this spec.
- If a future epic ever wants a fifth access model (e.g. Beszel or AdGuard exposed with per-user auth to family members, similar to Syncplay's friend-facing model), that's a new epic, not a retrofit of this one.
