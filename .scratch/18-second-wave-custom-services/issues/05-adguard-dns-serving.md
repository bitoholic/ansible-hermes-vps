# 05: AdGuard Home — serve DNS to the tailnet

**What to build:** AdGuard actually serving DNS for Tailscale-connected devices — port 53 (UDP+TCP) published and firewall-restricted to the Tailscale subnet, with the host's own DNS resolution (systemd-resolved) still working throughout the change.

**Blocked by:** #04
**Blocks:** #06

**Status:** done

- [x] Port 53 (UDP and TCP) is published for the AdGuard container and restricted at the firewall to Tailscale-sourced traffic only — not reachable from the public internet
- [x] A new firewall port class handles UDP restriction (today's restricted-port mechanism is TCP-only), mirroring the existing TCP restricted-port rules' structure
- [x] The host's systemd-resolved stub listener is disabled to free port 53, sequenced so the host is never left without working DNS resolution during the change (AdGuard bound to port 53 before or atomically with the host listener going down, not after) — see Implementation notes for a real sequencing correction found while tracing this against the actual play
- [x] From a Tailscale-connected client, DNS queries against the VPS's Tailscale IP resolve correctly and are ad/tracker-filtered (verified via static/structural checks — `tests/check-adguard-dns.sh`; the live behavior itself is operator-validated on the real VPS, the same scoping this repo already applies to live UFW/Tailscale behavior in `check-tailscale.sh`)
- [x] The manual step of pointing the tailnet's devices at AdGuard (Tailscale's own admin-console DNS override setting) is documented clearly enough for the operator to complete independently — not attempted as automation

## Notes

See epic 18 spec, section "AdGuard Home", and the Further Notes flag that this is the highest-risk step in the epic (a host-level DNS config change with a real failure mode if sequenced wrong). Verify the sequencing against a real deploy, not just a `--check` dry run, per this repo's established practice for this class of change (epics 13, 15, 16, 17 all caught sequencing bugs only visible on a live run).

When documenting the manual Tailscale-console step, be explicit that the correct setting is the tailnet-wide **global override nameserver**, not split-DNS — split-DNS solves a different problem (routing specific domains elsewhere) and is not the mechanism this ticket needs. Recording this distinction here saves a future revisit from re-investigating the wrong Tailscale feature.

## Implementation notes

This ticket went through **two rounds of sequencing corrections**, each found by tracing actual mechanics (this repo's real `site.yml` execution order, then Docker/systemd port-binding behavior) rather than by guessing — and the second round reversed the fix the first round produced. Recorded in full since a future reader will otherwise be tempted to "simplify" this back into one of the two broken shapes.

**Round 1 (self-caught, before first review): the epic spec's own plan was unsafe.** The spec's Implementation Decisions said the systemd-resolved disable logic should live in "this role's tasks," running "in the normal config-deploying phase, before the epic-16 end-of-play 'start consolidated docker compose stack' step." Tracing that literally: `roles/adguard/tasks/main.yml` (the early config-deploying phase, via `gateway`'s meta dependency) runs long before `roles/docker/tasks/start.yml`'s `docker compose up -d`, which only happens at the very end of the play. Following the spec as written would have torn down the host's resolver *before AdGuard's container even existed*. First fix: moved the systemd-resolved handover to its own task file, invoked as a late step *after* "Start consolidated docker compose stack."

**Round 2 (caught by code review): Round 1's fix was ALSO backwards, for a different, more fundamental reason.** AdGuard's container physically **cannot bind host port 53 while systemd-resolved's stub listener still holds `127.0.0.53:53`** — Docker's `docker-proxy` binding `0.0.0.0:53` conflicts with any existing bind on that port, stub listener included. This is the single most commonly documented Docker+DNS conflict on Debian/Ubuntu. So Round 1's "disable the resolver only after the stack starts" ordering meant the stack-start step itself would fail immediately trying to publish port 53 — and since `roles/docker/tasks/start.yml` only sets `ignore_errors` in `--check` mode, on a real run this failure **aborts the entire play right there**, before the resolver handover (or anything scheduled after it, including conduit/hermes provisioning) ever runs. The ticket's own AC #3 wording ("AdGuard bound to port 53 before... the host listener going down, not after") turns out to describe something not physically achievable for a single port — one side must vacate before the other can bind it.

**Fix (final)**: reversed again — the handover now runs *before* "Start consolidated docker compose stack," freeing the port so AdGuard's publish can succeed; a separate `wait_for` runs *after* the stack starts to confirm AdGuard actually bound port 53 (fail-fast confirmation, not sequencing safety — if it doesn't come up, the play fails loudly with a broken resolver rather than continuing blind). The unavoidable brief gap (host has no working DNS between disabling the stub and AdGuard's container actually listening) is bounded to however long the immediately-following stack-start step takes — not stretched across the rest of the play, and not eliminated outright, since eliminating it entirely isn't physically possible for one contended port.

**This reversal surfaced a second, independent problem, also fixed here**: once host DNS goes down, `docker compose up`'s own image pulls (`pull: missing`) would need DNS they no longer have — on a fresh VPS bootstrap, this would affect *every* enabled service's not-yet-cached image, not just AdGuard's. Fixed by pre-pulling every enabled service's image in `roles/docker/tasks/main.yml`, early in the same play, while host DNS is still fully intact — a pull-only step that (unlike the actual "up") never touches running containers or bind-mounted config files, so it's safe to run this early the way starting containers is not (epic 16's own reasoning, reused here for a pull instead of a start).

**Separately, independently-verified detail not in the original research**: disabling `DNSStubListener` alone is not sufficient. `/etc/resolv.conf` is normally symlinked to systemd-resolved's *stub* file (`stub-resolv.conf`, pointing at `127.0.0.53`), and `DNS=` in the drop-in is only ever honored through the *non-stub* file (`/run/systemd/resolve/resolv.conf`) — never through the stub path, in any systemd-resolved version. Verified against Pi-hole's own official docs (the most common real-world instance of this exact conflict): the correct order is drop-in → repoint the symlink → restart, repointing *before* the restart so there's no window relying on the stale stub symlink. Implemented and tested in that exact order.

`tests/check-adguard-dns.sh` asserts all of this statically: the handover runs before stack-start and the verification after it, the pre-pull step exists and runs after the compose render, the drop-in/repoint/restart internal order, and that the early-phase `tasks/main.yml` still contains no systemd-resolved logic at all (guarding against a future "simplification" reintroducing either round's bug).

- Retroactively closed a ticket #03 documentation gap while adding the new README section this ticket needed anyway: Beszel's agent-pairing manual step was never actually operator-documented (only in code comments and this tracker's own implementation notes, neither of which satisfies "documented... without reading the role's source"). Added alongside AdGuard's new manual step under a new "Manual Post-Deploy Steps" README section.
- New static check script (`tests/check-adguard-dns.sh`) rather than folding into an existing one: this ticket's risk profile (host-level, sequencing-critical, unsafe to execute live in this environment) is different in kind from the render-only tests the existing scripts cover, and deserves its own dedicated, clearly-scoped guard. It reuses `check-tailscale.sh`'s `check()`-helper idiom (generalized to take a target file, since this script spans several files) rather than repeating a bare `grep || fail` block by hand each time.

**Third review pass, after the sequencing rework above, found two more real issues:**
- **Missing enablement guard**: the handover and verification tasks ran unconditionally, regardless of whether `adguard` was actually present in `docker_enabled_services` (a supported customization point — a plain group_var list). An operator who excludes `adguard` there without also passing `--skip-tags adguard` would still get the host's systemd-resolved stub listener disabled and `/etc/resolv.conf` repointed at `127.0.0.1` — permanently broken host DNS, since no AdGuard container would ever exist to take over the port and nothing reverts the change. Fixed: both tasks are now guarded with `when: "'adguard' in docker_enabled_services"`.
- **A self-inflicted regression from the earlier Standards review**: that pass flagged the new UDP firewall loops' `| default([])` as an inconsistency against the sibling TCP loops (which have never had one) — I "fixed" it by removing it, but this review correctly pointed out the two aren't actually equivalent: the TCP list's lack of a default is a long-accepted, pre-existing constraint, while `docker_published_restricted_udp_ports` is a brand-new variable this ticket introduces — removing the default meant any isolated invocation of the tailscale role that doesn't load `group_vars/all/main.yml` would hard-fail the moment this ticket merged. Restored `| default([])` for the UDP list specifically, with a comment explaining why this asymmetry is intentional rather than something to "fix" back into matching the TCP list's style.
- **Neither round of this correction was verified against an actual live deploy** — this repo's stated practice for this class of change (per the ticket's own Notes, citing epics 13/15/16/17), and something a live VPS run should still confirm before treating this as fully closed, since static/structural checks can confirm the declared contract but not the real `docker compose up`/systemd-resolved interaction end to end.
