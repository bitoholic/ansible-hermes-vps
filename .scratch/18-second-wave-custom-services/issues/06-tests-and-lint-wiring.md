## Implementation notes

Because tickets #01–#05 each already extended the shared render tests (`test_docker_compose.yml`, `test_gateway_render.yml`) and their own dedicated scripts (`check-adguard-dns.sh`) incrementally as they landed, most of this ticket's scope was already delivered piecemeal — this ticket's real remaining work was auditing what was actually covered versus what the ACs literally ask for, and closing the gaps found:

- **AC #2 (firewall) had a real gap**: `test_docker_compose.yml`'s "every published port belongs to a declared class" check only ever validated against its own hand-maintained mirror of `docker_published_restricted_ports`/`docker_published_public_ports` — never against the real `group_vars/all/main.yml`. Nothing would have caught the production file and the test's mirror drifting apart. Added a direct check (`tests/check-second-wave-services.sh`) confirming Beszel's 8090 and AdGuard's 3001 are actually present in the real file.
- **AC #3 (secrets shape) had a real gap**: the existing env-catalog sync check confirms `.env.template`/`setup-env.sh` match the manifest, but nothing independently verified the manifest itself declares the *right* `required`/`default` values — specifically that `beszel_agent_key`/`beszel_agent_token` stay `required: false` (ticket #03's near-miss deploy-deadlock fix) and `adguard_admin_password_hash` stays `required: true`. A future accidental flip of either would have shipped silently. Added explicit shape assertions.
- **AC #4 (role-ordering) had a real gap**: `tests/check-role-ordering.sh` (epic 15) only ever asserted this for `owntracks`; `beszel` and `adguard` had never gotten the equivalent three-part proof (meta dependency declared, no explicit `site.yml` entry, exactly-once execution) despite being wired in the identical way. Extended the existing script rather than creating a parallel one, since this is exactly the file a future reader would look in for this class of guarantee.
- **AC #1 and #5 were already fully satisfied** by tickets #02–#04's own work; re-verified rather than re-implemented.
- New consolidated script named `tests/check-second-wave-services.sh` (not folded into `check-adguard-dns.sh`, which stays scoped to ticket #05's DNS-sequencing specifics) — mirrors epic 12's `check-custom-services.sh` exactly, including its convention of re-invoking the shared render tests and re-asserting things already checked elsewhere (env-catalog sync, skip-tags membership) as a single, self-contained epic-wide pass, per the epic spec's own explicit Prior Art note naming this file.
- One naming surprise while extending `check-role-ordering.sh`: `beszel`'s and `adguard`'s own directory-bootstrap tasks (both call `include_role: name: wiki_volume, tasks_from: ensure_directory`) show up in `--list-tasks` *without* a `"<role> : "` prefix, unlike a plain module task (e.g. `owntracks`'s "Generate htpasswd..." or `adguard`'s own "Assert mandatory secrets are present" — both correctly prefixed). First attempt at the new ordering check used the prefixed form and silently matched zero tasks; fixed by using the actual unprefixed name Ansible renders for a task that itself delegates via `include_role`.

**Code review found a real bug in this ticket's own new script, and the fix surfaced an identical, pre-existing bug already merged from ticket #05.** `check-second-wave-services.sh`'s original `list_has` helper used a fixed `grep -A10` window — too generous for checking one specific YAML entry's field when a similarly-shaped entry sits nearby. Reviewer verified empirically: flipping `beszel_agent_key`'s `required:` to `true` (the exact regression the check exists to catch) still printed "OK", because the 10-line window starting at `beszel_agent_key:` extended into `beszel_agent_token`'s own unrelated `required: false` three lines later. While fixing it, I checked whether `check-adguard-dns.sh` (ticket #05, already merged) had the identical shape for its own "53 in `docker_published_restricted_ports`" check — it did, verified the same way (temporarily deleting `- 53` from the TCP list; the check kept passing because its window bled into `docker_published_restricted_udp_ports`'s own `- 53` right after the TCP list ends). Fixed both with the same approach: a small helper that bounds the search to the actual YAML block (from the key line up to, but excluding, the next line at the same indentation level) instead of a fixed line count. Verified both fixes by reproducing each regression scenario, confirming the check now fails, then reverting.

**A second review pass on this same ticket found one more spec-named gap, ironic given this ticket's whole purpose**: `spec.md`'s own Testing Decisions explicitly calls for verifying `docker_enabled_services` includes all four new services and `docker_volumes` gained no new entries — against the real file (`roles/docker/defaults/main.yml`, not `group_vars/all/main.yml` as the spec's prose slightly misstates it), not `test_docker_compose.yml`'s own hardcoded mirror of both lists. This is the exact class of gap the first pass already found and fixed for the firewall ports, just not extended to this identically-shaped, spec-named item. Added both checks to `check-second-wave-services.sh` and verified each by reproducing a regression (removing a service from `docker_enabled_services`, removing an entry from `docker_volumes`) and confirming the check now fails, then reverting.

The same review also flagged the `list_has`/`entry_has` split as duplicated bug-fix logic under two different names across two files. This repo's test scripts are each self-contained by convention (no shared-helpers file exists anywhere), so full extraction would be a bigger, out-of-scope change — but renamed `check-adguard-dns.sh`'s `list_has` to `entry_has` (identical implementation, now identical name) so the two aren't a confusing near-identical-but-differently-named pair, with a cross-reference comment in both files.

**A third review pass found two more small things, both fixed**: the `docker_volumes` check added above was exact-count (must be exactly 3), but the sibling `docker_enabled_services` check was presence-only (the 4 new services must appear) with no count assertion — a duplicate entry or an unrelated, unauthorized 5th addition could have slipped through undetected. Added the same exact-count rigor (12 = the 8 pre-epic-18 services + this epic's 4), verified by reproducing the regression (adding an unauthorized entry, confirming the check now fails) and reverting. Also: the `list_has`→`entry_has` rename's cross-reference comments in both files still claimed "same name/shape" after `check-second-wave-services.sh`'s own version had already been split into `block_of` + a thin `entry_has` wrapper (needed for the new count checks' raw-block access) — no longer byte-identical in shape, just in name and contract. Reworded both comments to say so accurately.
