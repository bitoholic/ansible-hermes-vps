# Spec: Reduce docker/wiki_volume Role-Execution Duplication

> Status: ready-for-agent
> Source: Epic 17 — explicitly recommended by epic 15 ticket #01's and epic 16 ticket #01's own Notes, and by the final all-branch review of PR #90 (merged to `main`), as "a dedicated epic... now scoped with real numbers"
> Related: `15-role-ordering-check` (the sibling epic this directly extends — same root cause, same "remove the explicit `roles:` entry" precedent this epic's Fix B follows for `owntracks`→`gateway`; also the epic whose own ticket #01 first misdiagnosed, then partially corrected, the wiki_volume duplication count), `16-start-stack-ordering-fix` (whose own ticket #01 first surfaced the 5×/11× numbers as a side effect of implementation, and whose deferred consideration of a `docker`→`gateway` dependency is directly affected by this epic's changes)
> Vocabulary: "role invocation", "meta dependency", "explicit entry", "tag inheritance" — no existing ADR governs Ansible role-invocation mechanics; this is infrastructure-tooling behavior, not an application-domain concept

## Problem Statement

Two roles execute far more often than once per `site.yml` run, on `main` today, unrelated to and predating epics 13–16: `docker`'s own tasks (engine install, network creation, compose-file render/validation, etc.) run **5 times**; `wiki_volume`'s own tasks (the `llm_wiki` uid/gid lookup, its assert, and its directory-bootstrap entrypoint) run **11 times**. Every one of these repeated executions is individually idempotent — no data changes, no errors — so this has gone unnoticed. But it wastes real time on every single deploy (5× an apt-update-and-install cycle, 11× a getent lookup and directory check), and it's a latent risk: any future task added to either role that *isn't* perfectly idempotent would silently inherit a 5× or 11× blast radius with nothing to catch it.

The root cause, confirmed empirically rather than assumed: Ansible's role-invocation deduplication is defeated by **tag inheritance**. When a role is pulled in as a `meta/main.yml` dependency, it inherits the calling role's own tags into its effective invocation identity. Two different parents pulling in the same dependency end up with different merged tag-sets (`docker` via `conduit` shows `TAGS: [conduit, docker]`; `docker` via `hermes` shows `TAGS: [docker, hermes]`), so Ansible treats them as distinct invocations of "the same role with the same vars" and does not deduplicate them against each other. This shows up in two variants: an explicit `site.yml roles:` entry not deduplicating against a dependency on the same role (already found and fixed for `owntracks`→`gateway` in epic 15 ticket #01), and — newly confirmed this session — multiple sibling roles independently depending on the same target role *also* not deduplicating against each other. The second variant directly contradicts a claim epic 15 ticket #01's own Notes originally recorded ("wiki_volume correctly runs once despite six roles depending on it") — later corrected once already (to "11 times, not once"), but without the underlying mechanism being understood until now.

## Solution

Apply the two verified-safe reductions this investigation actually measured, and put a regression test around the result so it can't silently get worse. This is **not** a full fix — after both changes, `docker` still runs 4 times and `wiki_volume` still runs 7 times, because fully eliminating the duplication runs into the tag-inheritance mechanism itself, which has no known clean workaround yet. The spec is deliberately honest about this rather than promising single-execution as an outcome it doesn't deliver.

## User Stories

1. As a VPS operator, I want `authelia`, `hermes`, and `silverbullet` to stop declaring `wiki_volume` as a direct dependency when they already depend on `docker` (which itself depends on `wiki_volume`), so that one redundant resolution path per role is removed with zero behavior change — the facts are already available transitively.
2. As a VPS operator, I want `docker` to stop being listed as its own explicit `site.yml roles:` entry, relying purely on its dependents' `meta/main.yml` dependencies to place it — matching the precedent already established for `owntracks`→`gateway` in epic 15 — so that one more redundant execution is removed.
3. As a VPS operator, I want the resulting shift in `docker`'s effective execution position (from its old explicit-entry spot to wherever its first remaining dependent now sits) verified safe, not assumed — specifically, that `gateway`'s tasks (which run in between `docker`'s old position and its new one) don't need `docker`'s engine/networks/rendered-compose-file to exist.
4. As a test author, I want a regression test asserting `docker`'s and `wiki_volume`'s task-execution counts don't exceed the levels this epic actually achieves (4 and 7 respectively), so a future change can't silently make the duplication worse without a test catching it.
5. As a future epic author, I want it clearly documented that this epic does **not** achieve single execution for either role, and why (tag inheritance defeating Ansible's role-dedup), so nobody mistakes the bounding regression test for "the bug is fixed" and quietly assumes more was delivered than actually was.
6. As a future epic author revisiting epic 15's deferred ticket #02 (`docker` depends on `gateway`), I want it documented that this epic's changes don't retroactively make that ticket safe — `docker` still resolves multiple times, so a new dependency on it would still multiply — so that ticket isn't reconsidered on a false assumption that this epic already cleared the way.
7. As a VPS operator, I want zero change to `docker_enabled_services`, any compose fragment, or the resulting deployed system's actual behavior — this epic only touches how many times two roles' own setup tasks run, not what they produce.
8. As a maintainer, I want the specific candidate ideas for a future full-elimination epic (breaking tag inheritance into dependency chains somehow; restructuring `docker`/`wiki_volume` as a one-time bootstrap play run before the main role list instead of via `meta/main.yml` dependencies; investigating other Ansible role-dependency options not yet explored) recorded somewhere discoverable, so that epic doesn't have to re-derive the problem from scratch.

## Implementation Decisions

- **Fix A — remove redundant sibling dependencies**: `roles/authelia/meta/main.yml`, `roles/hermes/meta/main.yml`, and `roles/silverbullet/meta/main.yml` each currently declare dependencies on both `wiki_volume` and `docker`. Since `docker` already transitively depends on `wiki_volume`, and Ansible fact resolution persists as global host facts for the rest of the play regardless of which dependency path resolved them first, the direct `wiki_volume` entry is redundant in all three. Remove it, keeping only the `docker` dependency. No behavior change — verified by measurement (wiki_volume count: 11 → 8; docker count unaffected: stays at 5 until Fix B is also applied).
- **Fix B — remove `docker`'s explicit `site.yml roles:` entry**: matches the precedent epic 15 ticket #01 already established for `owntracks`. `docker` remains a `meta/main.yml` dependency of `conduit`, `hermes`, `authelia`, and `silverbullet` — removing only its own separate top-level listing. Verified by measurement, applied alone: docker count 5 → 4 (not to 1 — the 4 remaining dependency-driven pulls don't dedupe against each other either, per the tag-inheritance root cause). Applied together with Fix A: docker = 4, wiki_volume = 7 — the combined, verified result this epic actually delivers.
- **No new dependency added to `wiki_volume` or `docker` themselves** — this epic only removes redundant/duplicate paths, it doesn't restructure the graph's shape otherwise.
- **`site.yml`'s remaining role list order is otherwise unchanged.** `docker`'s effective execution position, once it's dependency-only, is wherever its first remaining dependent (`conduit`) sits — which is exactly where `docker`'s own explicit entry used to be, since `conduit` was already the next role listed after `docker`. This is a coincidence of the current list order worth stating plainly, not a coincidence to rely on blindly in a future reorder — the ticket must verify it via `--list-tasks`, not assume it from this description.
- **Full elimination of the remaining duplication (docker 4×, wiki_volume 7×) is explicitly not attempted in this epic.** The tag-inheritance mechanism has no verified clean workaround yet. Candidate approaches for a future epic (not designed here, just recorded): preventing tag propagation into dependency-pulled roles; restructuring `docker`/`wiki_volume` as a one-time bootstrap play run before the main role list rather than via `meta/main.yml` dependencies at all; other Ansible role-dependency mechanisms not yet explored this session.

## Testing Decisions

- **What makes a good test**: verify actual, measured execution counts against the real `site.yml` (via `ansible-playbook site.yml --list-tasks`), not code inspection or assumption — this whole epic exists because an earlier, unverified assumption about deduplication turned out to be wrong.
- **Modules tested**:
  - A regression test asserting `docker`'s own task count (e.g. count of "docker : Validate Docker role prerequisites" in `--list-tasks` output) is `<= 4`, and `wiki_volume`'s own task count (e.g. count of "wiki_volume : Lookup llm_wiki passwd entry") is `<= 7` — bounding the duplication at the level this epic delivers, catching a future regression that makes it worse. Explicitly not asserting `== 1` for either, since that's not what's being delivered; a test asserting exact-once would be a false promise.
  - An ordering test (mirroring `tests/check-role-ordering.sh`'s and `tests/check-stack-start-ordering.sh`'s existing `--list-tasks`-based structural-proof pattern) asserting `docker`'s (now dependency-only) tasks still run before `conduit`'s/`hermes`'s/`authelia`'s/`silverbullet`'s own config-phase tasks, and before the epic-16 end-of-play "Start consolidated docker compose stack" step.
  - Static checks that `roles/authelia/meta/main.yml`, `roles/hermes/meta/main.yml`, and `roles/silverbullet/meta/main.yml` no longer declare `wiki_volume` directly (only `docker`), and that `site.yml` no longer has an explicit `role: docker` entry.
- **Prior art**: mirror `tests/check-role-ordering.sh` (epic 15) and `tests/check-stack-start-ordering.sh` (epic 16) — both already establish the `--list-tasks`-based verification pattern this epic's tests extend rather than reinvent.

## Out of Scope

- **Fully eliminating the remaining duplication** (`docker` still 4×, `wiki_volume` still 7× after this epic) — the tag-inheritance root cause has no verified clean fix yet; a future epic's territory, candidate approaches recorded in Implementation Decisions and Further Notes.
- **Revisiting epic 15's deferred ticket #02** (`docker` depends on `gateway`) — this epic's changes do not retroactively make that safe (`docker` still resolves multiple times), so that ticket stays deferred. Worth reconsidering together with whatever epic eventually achieves full elimination, not decided here.
- **Any change to `docker_enabled_services`, compose fragment content, or deployed system behavior** — this epic only touches role-invocation counts.
- **Investigating or fixing tag inheritance in Ansible itself, or reworking this repo's tagging/skip-tags scheme** (epic 10) to avoid the mechanism — out of scope; the skip-tags feature stays as-is.

## Further Notes

- This epic is the direct, explicitly-requested follow-up to findings surfaced during epics 15 and 16's implementation (both already merged as part of PR #90) — not a new architecture-review candidate, a cleanup of a specific, numerically-verified problem those epics found but correctly declined to fix inline (staying within their own scope).
- **The investigation for this spec was done empirically**: the current `roles/*/meta/main.yml` dependency graph was read directly (not assumed), and both Fix A and Fix B (and their combination) were tested by temporarily editing the real files, measuring the resulting `--list-tasks` counts, and reverting (`git diff` confirmed clean afterward) — the numbers in this spec are measurements, not estimates.
- Open question left to the implementer, not decided here: whether the bounding regression test should hard-code the exact numbers (4 and 7) or use a named constant/comment explaining what they mean and why they're not 1 — either is fine, but whichever is chosen should make it obvious to a future reader that these are a *known, accepted ceiling*, not an arbitrary threshold.
- Candidate ideas for a future full-elimination epic, recorded here so that epic doesn't start from zero: (a) investigate whether Ansible's role-dependency system has any option to prevent tag inheritance/merging into a pulled-in dependency's effective identity; (b) restructure `docker` and `wiki_volume` as a one-time bootstrap sequence (e.g. a `pre_tasks`-level `import_role` at the very start of the relevant play) that every other role can assume has already run, rather than relying on `meta/main.yml` dependencies at all for these two specifically; (c) survey whether `community.general` or Ansible core has grown any other relevant role-deduplication controls since this was last checked.
