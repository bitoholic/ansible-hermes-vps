# Spec: Cloudflare-Proxied Ingress for Matrix and OwnTracks

> Status: ready-for-agent (no longer draft — grill/me decision on the Caddy build approach captured)
> Source: Epic 19 — "explore switching matrix/owntracks Cloudflare DNS to proxied", raised as a follow-up during epic 18's design work but scoped as its own epic since it changes *existing* services' ingress/TLS handling, not the onboarding of new ones
> Related: **Supersedes ADR-0003** (matrix's public ACME cert and the "DNS record is direct/not proxied" decision) — this epic changes that decision's premise, so ADR-0003 must be marked superseded, not silently contradicted; `12-add-custom-services` (origin of the `:8448` SNI-sharing decision between matrix and owntracks); `03-gateway-reverse-proxy` (the Caddyfile/gateway seam this epic's changes land in); `13-gateway-route-schema` (the `port`/`tls_mode` fields this epic reuses — no schema change needed, only two existing routes' field *values* change)
> Vocabulary: "proxied DNS record" (Cloudflare "orange cloud" — traffic passes through Cloudflare's edge, origin IP hidden), "grey-clouded / DNS-only record" (current state for matrix/owntracks — resolves directly to the VPS's IP), "Cloudflare proxied-port allowlist" (the fixed set of ports Cloudflare's standard proxy forwards; excludes 8448, includes 8443), "DNS-01 challenge" (ACME domain-ownership proof via a DNS TXT record — no inbound reachability required), "HTTP-01 / TLS-ALPN-01 challenge" (Caddy's default ACME methods today — both require the origin to be directly reachable, which a proxied record breaks), "xcaddy" / "Caddy builder image" (Caddy's own official mechanism for compiling in third-party plugins)

## Problem Statement

`wiki`, `dash`, `auth`, and `syncplay`'s DNS records are Cloudflare-proxied ("orange cloud") — Cloudflare's edge fronts them, hiding the VPS's origin IP and applying Cloudflare's DDoS/edge protection. `matrix.<domain>` and `owntracks.<domain>` are not: both are "grey-clouded" (DNS-only, resolving directly to the VPS's public IP), leaving those two hosts' origin IP exposed and without Cloudflare's edge protection, which the operator finds inconsistent and would prefer to fix now that the rest of the stack is stable.

ADR-0003 documents *why* matrix (and, by the same reasoning, owntracks — both share Caddy's `:8448` SNI listener) were left grey-clouded: Caddy's automatic HTTPS obtains a real Let's Encrypt certificate via a challenge (HTTP-01 or TLS-ALPN-01) that requires the ACME validation traffic to reach the origin server directly. If Cloudflare proxies the record, that traffic is intercepted/terminated at Cloudflare's edge instead of reaching Caddy, and certificate issuance fails.

**This epic's own research surfaced a second, independent blocker ADR-0003 didn't call out**: Cloudflare's standard proxy plans (Free/Pro/Business — not the paid Spectrum add-on) only forward a fixed allowlist of ports for proxied HTTP/HTTPS traffic. Port **8448 is not on that list**; port **8443 is**. This means even if the certificate-issuance problem were solved on its own, a proxied record on `:8448` still would not route traffic to the origin at all — Cloudflare's edge simply doesn't relay that port. Both blockers must be resolved together; solving either alone does not unblock proxying.

## Solution

Two coordinated, interdependent changes to the existing matrix/owntracks routes (no new services, no new gateway routes — this is a migration of two routes' existing `port`/TLS configuration, values only):

1. **Move the shared SNI listener from `:8448` to `:8443`** for both the `matrix` and `owntracks` (recorder) gateway routes — `:8443` is on Cloudflare's proxied-HTTPS-port allowlist; `:8448` is not.
2. **Switch Caddy's certificate-issuance method for those two routes from HTTP-01/TLS-ALPN-01 to DNS-01**, authenticated via a Cloudflare API token (the `caddy-dns/cloudflare` module) — DNS-01 proves domain ownership by publishing a DNS TXT record via the Cloudflare API, requiring zero inbound reachability to the origin, so it works correctly even once the DNS record is fully proxied.

Since the Cloudflare DNS plugin isn't part of Caddy's official Docker Hub image, Caddy is built from a local Dockerfile using Caddy's own official `xcaddy` builder image (`caddy:<version>-builder`) — mirroring this repo's existing pattern of building `hermes-agent` from its own local Dockerfile rather than pulling a pre-built third-party image. This was a deliberate, grilled choice over a community-maintained pre-built plugin image: Caddy is this stack's single ingress/TLS-termination point for *every* service, including the ones this epic doesn't otherwise touch, so trusting a third party's build pipeline for it is a materially bigger risk than doing so for any individual service's own image.

Only once the new cert-issuance path is verified working (a real Let's Encrypt cert obtained and served, with the DNS record still grey-clouded — DNS-01 doesn't care about the record's proxy status, so this can be verified in place before any cutover) are the `matrix.<domain>` and `owntracks.<domain>` DNS records flipped to Proxied in the Cloudflare dashboard — a manual, external-console step; this repo has no existing DNS-record automation (no Terraform/Cloudflare-API-managed zone), so this was always going to be a manual step, unrelated to anything Ansible could take over.

## User Stories

1. As a VPS operator, I want `matrix.<domain>` and `owntracks.<domain>` proxied through Cloudflare like `wiki`/`dash`/`auth`/`syncplay` already are, so that all my public-facing hosts get consistent origin-IP-hiding and edge protection.
2. As a security reviewer, I want the VPS's origin IP no longer directly resolvable for matrix and owntracks, so that its exposure is consistent with the rest of the public surface rather than an exception.
3. As a maintainer, I want it documented and verified — not assumed — that port 8448 is not on Cloudflare's proxied-port allowlist while 8443 is, so that this epic's port move is grounded in the actual current Cloudflare product behavior, not folklore.
4. As a VPS operator, I want the shared SNI listener moved to `:8443` for both matrix and owntracks together (they must move together — they still share one listener), so that the SNI-routing relationship established in epic 12 isn't broken by moving only one of the two.
5. As a Matrix client user, I want my homeserver URL to keep working with an updated port (`https://matrix.<domain>:8443` instead of `:8448`), so that I know exactly what to reconfigure — and I want it explicit that this is a one-time manual client-side update, not something Ansible can push to my device.
6. As a mobile OwnTracks app user, I want the same one-time manual update to my app's configured server port, so that I know why location reporting would otherwise stop working after this ships.
7. As a VPS operator, I want Caddy's certificate issuance for matrix and owntracks switched to DNS-01 via a Cloudflare API token, so that certificate renewal keeps working indefinitely once the DNS record is proxied (HTTP-01/TLS-ALPN-01 would permanently break at that point).
8. As a security reviewer, I want the Cloudflare API token scoped to the minimum privilege needed (`Zone:DNS:Edit` on the one zone), stored as a new secrets-manifest entry, so that a leaked token can't do more than manage that zone's DNS records.
9. As a maintainer, I want Caddy built from this repo's own Dockerfile via Caddy's official `xcaddy` builder image, not a third-party pre-built image, so that the stack's single TLS-termination point for every service doesn't depend on trusting an external build pipeline.
10. As a maintainer, I want the DNS-01 directive scoped to only the matrix and owntracks route blocks in the Caddyfile (not a global default issuer), so that `wiki`/`dash`/`auth` (which use `tls internal`, no ACME at all) and any future `tailnet_only` route are provably unaffected by this change.
11. As a VPS operator, I want the new certificate obtained and verified working *before* the DNS record is ever flipped to proxied, so that there's no window where clients see a broken TLS handshake mid-migration.
12. As a VPS operator, I want the actual Cloudflare dashboard DNS-record flip documented as an explicit manual step (this repo doesn't manage DNS records via any API/Terraform automation today), so that it's clear Ansible's job ends at "the origin is ready for a proxied record," not "the record is now proxied."
13. As a future epic author or reviewer, I want ADR-0003 marked superseded (not deleted, not silently contradicted) by whatever ADR results from this epic, so the historical reasoning stays legible and the current state is unambiguous.
14. As a maintainer, I want Cloudflare's SSL/TLS encryption mode implication noted (once the origin has a real trusted Let's Encrypt cert, "Full (strict)" becomes viable/preferable over "Full" for these two hosts specifically), so a future review knows this was considered, even though changing that dashboard setting is also a manual Cloudflare-console step outside Ansible's reach.
15. As a maintainer, I want this epic to leave the `wiki`/`dash`/`auth`/`syncplay` routes and their existing `tls internal`/proxied setup completely untouched, so this is provably a two-route migration, not a stack-wide TLS redesign.
16. As a maintainer, I want epic 18's `tailnet_only` routes (OwnTracks frontend, Beszel hub, AdGuard admin UI) explicitly noted as unaffected by this epic — they use `tls internal`, no ACME, no public DNS record — so nobody conflates the two epics' scopes.

## Implementation Decisions

- **Port move**: `conduit_gateway_publish`'s `matrix` entry and `owntracks_gateway_publish`'s recorder entry both change `port: 8448` → `port: 8443`. No other fields on either entry change (both keep `mfa: false`, `tls_mode: "auto"`). This is a value change to two existing schema-conformant entries, not a schema change.
- **Caddy image**: replace the stock `caddy` image reference in `roles/docker/templates/services/caddy.yml.j2` with a `build:` context pointing at a new local Dockerfile (mirroring `hermes-agent.yml.j2`'s existing `build: context:`/`dockerfile:` pattern), using Caddy's official `caddy:<pinned-version>-builder` image as the build stage and `xcaddy build --with github.com/caddy-dns/cloudflare` to produce the final binary, copied into a matching `caddy:<pinned-version>` runtime stage. The Caddy version is pinned explicitly (not `:latest`) in both build and runtime stages so a plugin build is reproducible and doesn't silently drift on rebuild.
- **New secret**: `cloudflare_api_token` (required, no default) in the secrets manifest — a Cloudflare API token scoped to `Zone:DNS:Edit` on the operator's zone only. Passed into the Caddy container as an environment variable the DNS-01 issuer directive reads (Caddy's Cloudflare module reads it via an env-var placeholder in the Caddyfile, not a literal value baked into the rendered config file).
- **Caddyfile change, scoped to exactly two route blocks**: the `matrix` and `owntracks` (recorder) site blocks each gain a `tls { dns cloudflare {env.CLOUDFLARE_API_TOKEN} }` directive (or equivalent per-site issuer override), while every other route's TLS handling (`tls internal` for `wiki`/`dash`/`auth`/`syncplay`'s Caddy-fronted pieces, and the epic-18 `tailnet_only` routes) is untouched. No global default-issuer change — DNS-01 is opt-in per site block, exactly for the two routes that need it.
- **Verification-before-cutover ordering**: deploy the port + DNS-01 changes and confirm (via `caddy adapt`/a live external check, per this repo's established practice of verifying gateway changes against a real run — see epics 13/15/16/17) that Caddy obtains a valid Let's Encrypt cert for both hosts on `:8443` *while the DNS records are still grey-clouded* (DNS-01 doesn't require the record to be proxied to succeed — this is exactly what makes an in-place verification possible with zero client-facing risk). Only after that succeeds does the operator manually flip both DNS records to Proxied in the Cloudflare dashboard.
- **DNS-record flip is out of Ansible's reach and stays manual** — this repo has no Cloudflare-API/Terraform-managed DNS zone today; the flip is a Cloudflare-dashboard action the operator performs once Ansible-side verification passes, the same category of manual, external-console step as obtaining `TAILSCALE_AUTHKEY`.
- **ADR-0003 is superseded, not edited in place.** A new ADR records this epic's decision (port move + DNS-01 + custom Caddy build) and explicitly references ADR-0003 as superseded, preserving the original incident/reasoning history rather than rewriting it.
- **Cloudflare SSL/TLS mode (Full vs. Full-strict) is noted but not an Ansible-managed setting** — once matrix/owntracks serve a real trusted cert, "Full (strict)" becomes viable for the zone; changing it is a manual dashboard action the operator can make independently, documented as a suggestion in the ADR/Further Notes, not implemented or enforced by this epic.

## Testing Decisions

- **What makes a good test**: test the rendered artifacts and the render-time contract, not live Cloudflare/Let's Encrypt behavior (this repo's existing tests already draw this line — e.g. `check-tailscale.sh` explicitly notes live UFW/Tailscale behavior is operator-validated on the VPS, not asserted in CI). The actual cert issuance and DNS cutover are operator-validated on the real VPS, per this repo's established practice for anything requiring live external state.
- **Modules tested**:
  - `roles/conduit/defaults/main.yml`, `roles/owntracks/defaults/main.yml` → both `gateway_publish` entries now render `port: 8443` (not 8448); every other field on both entries is unchanged (regression test against the pre-epic values, similar in spirit to epic 18's "recorder route unchanged" assertions).
  - `roles/gateway/templates/Caddyfile.j2` → renders the `tls { dns cloudflare ... }` directive inside exactly the `matrix` and `owntracks` blocks, and *not* in `wiki`/`dash`/`auth`/`syncplay`-adjacent blocks or any epic-18 `tailnet_only` block; both routes render on `:8443`, not `:8448`.
  - `roles/docker/templates/services/caddy.yml.j2` → renders a `build:` context (not a stock `image:` pull) pointing at the new local Dockerfile; the Dockerfile pins an explicit Caddy version in both its builder and runtime stages (no `:latest`).
  - `group_vars/all/secrets.yml` → `cloudflare_api_token` present, `required: true`, no default.
  - `setup-env.sh` / `.env.template` — prompts for the new secret (`scripts/generate-env.py --check`).
  - `docker compose config` — the consolidated render still passes with Caddy's fragment now building rather than pulling.
  - A regression assertion (mirroring epic 18's approach) that every *other* existing route's rendered Caddyfile block is byte-identical to its pre-epic form — proving this is a scoped two-route migration.
- **Prior art**: mirror `tests/check-gateway-render.sh`/`tests/test_gateway_render.yml` for the port-value and DNS-01-directive assertions; mirror `tests/check-docker-compose-render.sh` for the Caddy build-vs-image render check; mirror `tests/check-resolver.sh`'s pattern for the new secret's required/no-default shape.

## Out of Scope

- **Proxying anything for `wiki`/`dash`/`auth`/`syncplay`** — already proxied (or, for syncplay, not Caddy-fronted at all); untouched by this epic.
- **Automating the Cloudflare DNS-record proxy-status flip** — no DNS-record-management automation exists in this repo today (no Terraform/Cloudflare-API zone management); introducing one is a separate, much larger epic if ever wanted, not bundled into this cert/port fix.
- **Automating the Cloudflare SSL/TLS encryption-mode change (Full → Full-strict)** — a manual dashboard setting, noted as a suggested follow-up, not implemented here.
- **Re-enabling Matrix federation** — still explicitly disabled (`allow_federation = false`), unrelated to and unaffected by this epic's port/cert changes.
- **Changing anything about epic 18's `tailnet_only` routes** (OwnTracks frontend, Beszel hub, AdGuard admin UI) — they use `tls internal`, no ACME, no public DNS record, and are unaffected by this epic regardless of implementation order relative to epic 18.
- **A generic/reusable "DNS-01 for any future route" mechanism** — this epic wires DNS-01 into exactly the two site blocks that need it now; generalizing it into a per-route schema field (e.g. an `acme_challenge: dns-01` option) is deferred until a third route actually needs it, consistent with this repo's stated aversion to building generality for a single (or even double) instance.

## Further Notes

- This epic's existence is itself evidence the epic-13 gateway-schema design is holding up: no schema change was needed here at all — `port` and `tls_mode` already existed as fields, and this migration is purely a *value* change to two already-conformant route entries, plus a template-level (not schema-level) addition scoped to those two blocks.
- **The Caddy-image decision was explicitly grilled**: building via Caddy's own official `xcaddy` builder (mirroring the existing `hermes-agent` local-Dockerfile pattern) was chosen over a community-maintained pre-built plugin image, specifically because Caddy is this stack's single TLS-termination point for every service — the trust/blast-radius calculus is different here than for any individual service's own container image.
- **Verification order is load-bearing, the same way epic 18's systemd-resolved sequencing is**: obtain and confirm the new DNS-01-issued certificate *before* touching the DNS record's proxy status, so there is no window where a client hits either a broken cert or an unreachable proxied port.
- The next natural follow-up, if this lands cleanly, is a small ADR update noting Cloudflare's "Full (strict)" mode is now viable for the zone — left as an operator decision, not designed here.
- Cross-reference for whoever implements this alongside epic 18: the two epics touch adjacent but non-overlapping surfaces (epic 18 adds new `tailnet_only` routes with `tls internal`; this epic changes two existing `tls_mode: auto` routes' port and cert-issuance method). They can be implemented in either order without conflict, but shouldn't be merged into a single ticket set — the review shape (schema addition + new services vs. TLS/cert-issuance migration for existing services) is different enough to keep separate, per the user's own framing of this as "another epic," not a folded-in ticket.
