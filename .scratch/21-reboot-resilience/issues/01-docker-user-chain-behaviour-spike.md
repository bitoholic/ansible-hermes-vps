# 01: Spike — how Docker treats a pre-populated DOCKER-USER chain

**What to build:** A recorded, reproducible answer — obtained in a disposable environment, never on the production VPS — to the questions the boot-persistence design depends on: when the Docker daemon starts, and when it restarts, does it preserve, flush or recreate a `DOCKER-USER` chain that already holds rules; can loading the rules *before* the daemon starts close the window in which published ports have no rules; and if not, how long is the window between daemon readiness and the rules being live. Delivers the concrete unit-wiring recommendation that ticket #02 builds.

**Blocked by:** None (can start immediately)
**Blocks:** #02

**Status:** done

- [x] The experiment runs in a disposable environment that matches the VPS's Docker version and firewall backend (a throwaway VM or nested daemon); if none is available on the workstation, the operator is asked for one — the production VPS is never used
- [x] Documented, with evidence, what happens to rules already in the chain on daemon start and on daemon restart, for both IPv4 and IPv6
- [x] Documented whether Docker adds or removes its own jump/return rules around the chain, and whether a rules load done *before* the daemon starts survives the daemon's startup
- [x] The exposure window between daemon readiness and rules being live is measured for each candidate wiring (before the daemon, after the daemon, a drop-in on the daemon's own unit), with the measuring method stated
- [x] A concrete wiring recommendation that satisfies the spec's required properties: idempotent, atomic, applied at boot and on every Docker restart, fail closed, and chain populated before containers start if and only if Docker preserves it
- [x] Findings and raw evidence are recorded in this ticket's notes so the later ADR can cite them

## Notes

See epic 21 spec, "Implementation Decisions" (required properties; mechanism decided by a spike). The existing role comment says the rules are "not persisted across reboot" and that the deployment model restores them by playbook run — that is the decision this epic reverses.

## Implementation notes

**Reproduce:** `.scratch/21-reboot-resilience/spike/run.sh build` (builds the image), then `./run.sh` (E1–E6) and `./run.sh e7` (exposure window, 10 alternating cycles per wiring). Raw output is in `spike/evidence/` (plain-text logs).

**Environment (the production VPS was never touched).** A rootless, privileged podman container with its own *private network namespace* — a private `DOCKER-USER` chain, unreachable from the workstation's or the VPS's firewall — running Ubuntu 26.04, `docker-ce 5:29.8.1` (the VPS's exact package version), `iptables v1.8.11 (nf_tables)` and Docker's `iptables` firewall backend. The harness **fails closed** outside such a container: each script checks `/run/.containerenv` (written by podman), that `guard.sh` is readable, that it loaded and defined its function, and then the guard's own checks (env flag, `/run/.containerenv` from podman *and* `name="hermes-spike"` in it — the name `run.sh` gives its container — and at most two network interfaces visible), and exits `2` at the first failure — verified by running both scripts directly on the workstation with the env flag set (both refuse with rc=2, touching nothing). `run.sh` refuses to run as root and forces a private network. (An earlier version let a failed `source` fall through; review caught it.)

**Method notes and differences from the VPS, disclosed:** "port live" means the DNAT/ACCEPT *rule appeared* — a conservative proxy (the earlier of the two), not a connection attempt; E7 timing covers **IPv4** published ports only (the loader still loads both families — E2/E3/E5 cover IPv6 chain behavior); wiring A's lead is measured from a `docker info` poll (a real `ExecStartPost` fires at `sd_notify`, tens of ms earlier than the poll, which does not change the sign);  the kernel is the workstation's (7.2.5, Fedora), not the VPS's; the storage driver is `vfs` (nesting); `ip_forward` was already 1 in the container, so Docker left the FORWARD policy at ACCEPT (the VPS's is DROP), which does not affect chain contents but does mean forwarding-policy behavior was not exercised; one container (the VPS runs 13 — restart concurrency, and so timing margins, differ); no `daemon.json` parity check; **no systemd inside** — unit ordering (`Before=`, `PartOf=`, `Requires=`) is not exercised and relies on systemd's documented semantics, verified on real systemd in the attended drill (#06). Between E7 cycles the harness flushes netfilter *and* deletes Docker's bridges (as a reboot would) but cannot reproduce a real boot's conntrack/kernel-module state.

**Findings**

| # | Question | Result |
|---|---|---|
| E1 | What does Docker create on a cold start? | An empty `DOCKER-USER` chain (a bare `-N`, no `RETURN`) for **both** IPv4 and IPv6, plus `-A FORWARD -j DOCKER-USER` then `-A FORWARD -j DOCKER-FORWARD`. The live VPS audit (this epic's source) found exactly this shape: a bare `-N DOCKER-USER` on both families. |
| E2 | Chain pre-populated **before** the daemon starts? | **Preserved**: 2/2 marker rules survive, IPv4 and IPv6; Docker adds its FORWARD jump and leaves the contents alone. |
| E3 | Daemon **restart** with a populated chain? | **Preserved**: 2/2 markers, both families; the FORWARD jump stays at exactly 1 (neither duplicated nor lost). Stopping the daemon leaves the rules in place. |
| E4 | Does creating a network / running a container touch the chain? | No — contents unchanged. |
| E4b | Daemon restart **while a restart-policy container is running**? | Chain intact (2/2 markers, both families), one FORWARD jump, and the container came back. |
| E5 | `iptables-restore --noflush` with the chain declared | Replaces **only** `DOCKER-USER` (old markers gone, not appended); Docker's own `DOCKER` chain byte-identical afterwards; FORWARD jump intact; a second application produces an identical chain. This test shows *scope and idempotence*, not atomicity. |
| E6 | Sampling probe while replacing the chain 300× | `--noflush`: **0** probes found the canary rule absent. Flush-then-append (the role's old behavior): **300** probes found it absent (a count of failed probes, not of cycles). **Read as a contrast, not a proof:** each probe is a ~30 ms forked sample, so it cannot see a sub-millisecond gap; atomicity itself rests on nftables' transactional commit (`iptables-restore` submits one netlink transaction). What it does show is that the old flush-then-append leaves the chain empty at essentially every sampled instant while a deploy runs. |
| E7 | Is a port ever live without its rule, from a cold state? | **Measured with an ordered event stream** (`nft monitor` started before the daemon; one totally ordered sequence of R = our rule lands, J = Docker's `FORWARD → DOCKER-USER` jump, N = the DNAT rule, F = the filter ACCEPT, Q = `docker info` first answers; "port live" = the earlier of N/F, deliberately conservative; the safe/unsafe verdict uses stream *order*, not timestamps). 10 alternating cycles per wiring. **Wiring A** (rules loaded right after the API answers, `ExecStartPost`-style): **UNSAFE in 10/10 cycles** — the port went live **470–1332 ms (median 759 ms) before the rule**. **Wiring B** (rules loaded before the daemon starts): **safe in 10/10**, the rule preceding the port by **1.94–2.10 s (median 1.99 s)**, with Docker's FORWARD jump also preceding the port every time. Absolute numbers vary between runs (an earlier run of the same script gave A: 431–832 ms; that log was not retained) but the sign never did. |
| E7 mechanism | *Why* is A unsafe? | **Evidenced, not inferred** (recorded for the sampled cycle — cycle 1, both wirings — in `evidence/e7-window.txt`). The DNAT (N) and filter accept (F) appear *before* Q (the API answering) — e.g. cycle 1, A: N at +1.32 s, F at +1.35 s, Q at +2.11 s — and dockerd's own log for the same cycle shows "Loading containers: start" → "Restoring containers: start" → "Loading containers: done" *before* "Daemon has completed initialization" / "API listen". The daemon restarts restart-policy containers, publishing their ports, while it is still initializing; "after the API answers" is therefore already too late. |

**Corrections recorded.** (1) An earlier version of this spike measured A by polling and reported "0 ms, rules won by ~66 ms". Review showed that measurement could not detect a positive window (the poll for the port only started *after* the rules loaded, and a forked `iptables` call costs ~30 ms — the size of the effect). The event-driven redesign above reverses that conclusion for A. Wiring B's result did not change. (2) A first version of the guard *failed open* (a failed `source` left the check undefined and the script ran on); found in review and fixed as described above.

**Not measured separately (reasoned, not measured):** a `docker.service` drop-in `ExecStartPost=` runs after the daemon reports ready — no earlier than wiring A, so at least as unsafe; an `ExecStartPre=` drop-in runs before the daemon starts and is equivalent to wiring B.

**Recommendation (adopted by #02).** Load the rules **before** the daemon starts: a `Type=oneshot`/`RemainAfterExit=yes` unit with `Before=docker.service`, enabled at boot. Tie it to Docker's lifecycle with `PartOf=docker.service` and `WantedBy=… docker.service` so every Docker (re)start re-runs the loader first (harmless when the chain survived, and covers a chain lost by other means). Load with `iptables-restore --noflush` for both families. The unit itself is enabled normally; **only the fail-closed coupling — a `docker.service` drop-in with `Requires=` on the unit — ships disabled** (absent) and is enabled by the attended drill. This satisfies every required property: idempotent, atomic (nftables transaction), applied at boot and on every Docker restart, fail closed (when the coupling is enabled), and the chain populated before any container starts (Docker preserves it, and the measurement shows the ordering holds).

**Notes handed to ticket #02 (from review):** the loader unit must have **no `ExecStop`/`ExecStopPost`** that touches the chain — `PartOf=docker.service` propagates a Docker stop/restart to it, and a flush there would empty the chain on every restart (#02 asserts this); and `iptables-restore` 1.8.11 (nf_tables) has **no `-w`/`--wait` flag**, so none is used (nft transactions do not use the xtables lock).
