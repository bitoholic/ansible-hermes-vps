# 05: Read-only live verification script and the reboot-drill procedure

**What to build:** A read-only script the operator runs from a workstation that proves the VPS is in the correct state — after any reboot, or any time they doubt it — and a written, rehearsed reboot-drill procedure that uses it. The script changes nothing on the VPS and never claims a pass it cannot support.

**Blocked by:** #02, #03, #04
**Blocks:** #06

**Status:** done (agent part); the drill itself is #06

- [ ] The script runs only read-only commands on the VPS (a documented allowlist) and changes nothing
- [ ] It verifies: the `DOCKER-USER` rules for both families equal the rendering; the boot firewall unit is enabled and active; every expected container is running; restart policies are as declared; Docker, Tailscale and UFW are enabled; the host resolves names (with AdGuard up — stopping and pausing it are attended drill steps, not something a read-only script can do); the public ingress ports answer; the tailnet-gated routes answer from the tailnet
- [ ] It includes an outside-in probe of the restricted ports that reports *inconclusive* — never *pass* — when the operator's route to the VPS is not a plain internet path (for example when the workstation's traffic goes through another VPN)
- [ ] It prints nothing sensitive and takes the target host as an argument or from the environment (run through epic 22's wrapper in script mode, the encrypted store supplies it — this ticket does not wait for epic 22)
- [ ] The reboot-drill procedure is documented: pre-flight (provider console access verified, an alternate tailnet path to the host verified, a baseline captured), the reboot, post-boot verification, the stop-AdGuard and pause-AdGuard resolve checks, the Docker-restart check, late-dependency observation, enabling the fail-closed coupling, and what to do if locked out (via the console)
- [ ] The procedure states the bounds under test (relay convergence, front door up, rules live)

## Implementation notes

**Deliverables.** `scripts/verify-live.sh` (the read-only verifier), `tests/check-live-verification.sh` (its guard, wired into `tests/lint.sh`), and the "Reboot drill" section of `docs/reboot-resilience.md` (bounds under test, pre-flight, an eight-step procedure that enables one staged switch at a time, and a lock-out / rollback section).

**Read-only by construction, not by promise.** Every remote command goes through one `remote()` function that refuses — before any connection is made — anything not on a documented allowlist or containing a shell metacharacter, so a mutating command cannot be sent even by a bug in the script. `--self-test` proves the refusal; the guard additionally audits every command a full run sends (17) against the allowlist and greps the script for mutating verbs and for any `ssh` call outside `remote()`.

**One SSH connection.** UFW's `limit 22/tcp` allows 6 new connections per 30 s per source and extends the block on further attempts. The first live smoke test of the script opened a connection per check and locked the operator's *own workstation* out of SSH for the duration of the limit (the VPS itself was never down). The script now multiplexes a single connection (`ControlMaster` + `ControlPersist`), a test asserts a single connection per run, and the drill doc carries the warning for the manual steps.

**Never claims a pass it cannot support.** Results are counted as PASS / FAIL / INCONCLUSIVE / SKIP and only FAIL changes the exit status; the summary says inconclusive and skipped checks are not passes. The outside-in probe of the restricted ports (including the templated `conduit_port` 8008, which a naive parse drops) reports INCONCLUSIVE when the workstation's route to the VPS goes through a tunnel, and a partial `docker inspect` or a `curl` returning 000 is INCONCLUSIVE rather than pass or fail. The domain used for tailnet-route probes is never printed (`<label>.<domain>`).

**Tests.** A fake `ssh` returns a healthy VPS (everything passes, every enabled service and both rule families verified) and then each fault the epic exists to catch (emptied chain, stopped container, wrong restart policy, disabled unit, ...) — each must be reported and must fail the run.

**Not verifiable here (attended drill, #06):** everything against a real reboot; the script was smoke-tested read-only against the real VPS before the code was deployed and correctly failed on the not-yet-deployed pieces.

**Review round 1 (six blocking items; fixed, each with a mutation-checked test).** (1) An unreadable container list silently verified *zero* containers and passed — now a FAIL, and the script reports "N of M expected containers verified". (2) The restricted-port probe could PASS with nothing probed, or with no route to the VPS at all — it now needs a positive control (a public port that answered), a non-empty port list and `timeout` on the workstation, else INCONCLUSIVE/FAIL, and it prints how many ports it probed. (3) Rule drift printed raw rules, which contain the Syncplay friend's address — now counts only (and a pure reordering is named as such, because order changes what a rule set allows); the host is no longer echoed either, and a test asserts no IP, host or domain appears in any scenario's output. (4) A dead SSH connection made every remaining check retry against UFW's rate limit — the first failed attempt (ssh status 255) now aborts the run with status 2, from a preflight *and* from `remote()` itself (tested for both an unreachable host and a connection that drops mid-run); a host starting with `-` is refused. (5) The guard had ~10 unprotected checks: it now has a fault scenario for each (unit disabled/inactive/mis-ordered, docker/tailscaled/ufw disabled, tailscaled/UFW inactive, cannot resolve, reordered rules) and drives the workstation-side probes through fake `ip`/`curl`/`timeout` (exposed port, dead public port, VPN route, no positive control, curl 000, 5xx, no domain, no `timeout`). Of 23 mutations of the script the guard catches all except one equivalent mutant (removing the preflight — `remote()`'s own abort covers it). (6) The drill's "Docker will not start" rollback opened a real exposure (restricted ports published with an empty chain); it now says so and gives the safe order (load the rules by hand, or stop the restricted-port containers immediately). Also applied: an explicit late-dependency-observation step (where `hermes-agent`'s retry behavior is finally observed), stop/pause steps as one line in the open session (AdGuard is the tailnet's DNS server, so a dropped session could otherwise strand it), the pre-flight baseline ordering, public ports and tailnet route labels derived from the repo's own config instead of hardcoded (the tailnet routes are now the `tailnet_only` ones — `adguard`, `monitor`, `owntracks-ui`; `wiki`/`dash` are MFA-gated, not tailnet-only), `tailscaled` active, a note that UDP 53 cannot be probed reliably, and a `mktemp` marker in the self-test.

**Review round 2 (three blocking items; fixed, mutation-checked).** (1) `remote … | grep -q` under `pipefail` could report a false FAIL on a healthy VPS when `grep` exits early and the sender gets SIGPIPE (reproduced with a slow multi-line fake `ufw status`) — every such check now captures the output first and tests the variable. (2) A tailnet route answering 404 (Caddy's `tailnet_only` matcher returns 404 when it does not see a tailnet source) could have been counted as a pass without the guard noticing — the guard now asserts 404/403/500 FAIL and 200/302/401 PASS. (3) The "nothing sensitive printed" test covered four scenarios; it now runs inside every runner, so every scenario, probe variation and broken-config run is checked for an IP address, host or domain (three leak mutations that were missed now fail). Also applied: negative allowlist self-tests (other files, other unit properties, `iptables -S/-L`, `docker logs`, …, 77 assertions), `BatchMode`/`-O exit` pinned, the restricted-port count derived from the config, the rollback path's missing "then start Docker", and the bounds table no longer claims a post-boot check can prove boot *ordering* (the `journalctl` evidence in drill step 4 does). Not changed: the public-port probe uses the VPS's own `src` address from `ip route get` (correct on this host, which has its public address on the interface; a NATed cloud VPS would need the resolved host instead); IPv6 restricted ports are covered by the rule comparison, not probed outside-in; equivalent mutants (preflight vs. `remote()`'s own 255 abort; `sleep 1`) are defence in depth.

**Review round 3 (one blocking item, a guard gap; fixed).** The script was correct, but the SIGPIPE fix had no regression test (the fake ssh answered instantly, so re-introducing `remote | grep -q` passed the guard). The fake now has a `slow-output` scenario (multi-line answers with pauses for `ufw status` and the `systemctl show` checks), plus a static check against `remote … | grep -q`; both pipe-grep mutants now fail the guard. Also closed: an unreadable public or Tailscale address must be INCONCLUSIVE (new `no-pub` / `no-tsip` scenarios), unreadable tailnet route labels must FAIL, and the workstation probes must run when `HERMES_VERIFY_SKIP_LOCAL` is unset.

**Review round 4: PASS** (no blocking items). Non-blocking items applied: the drill's stop/pause steps claimed a one-line `a; b; c` survives a dropped session — it does not (SIGHUP skips the rest), so they are now a `( trap '' HUP; … )` subshell with a "reconnect by the Tailscale address and `docker start adguard`" fallback; the fake `curl` asserts the probe resolves to the VPS's *Tailscale* address on 443; every restricted port, including the templated conduit port, is tested as exposed; and the guard asserts non-`tailnet_only` routes are not probed. Unchanged (accepted): public-port probe uses the VPS's own `src` address (see round 2), `ControlPath` length on long `$TMPDIR`s (not relevant on this workstation).

**Found live during the drill's baseline (2026-09-24): a false FAIL from an intercepting network.** The first real run reported `FAIL restricted TCP port(s) reachable from the internet: 53`. Investigation (read-only): the VPS's rules were correct and its counters did not move during the probe — the *operator's own network* answers TCP 53 on **any** address (a probe of RFC 5737 TEST-NET-3 addresses, which cannot be real hosts, also connected and returned DNS answers). The outside-in probe therefore needs a **negative control**: each restricted port is also probed on `203.0.113.1`; if that answers too, the port is reported **INCONCLUSIVE** (never a leak, never a pass), while a real leak on a non-intercepted port still fails. Tested (`FAKE_INTERCEPT_PORTS`: intercepted port inconclusive and the rest verified; a real leak still fails next to an intercepted port; every port intercepted means no PASS) and mutation-checked (control removed, inconclusive turned into pass/verified/ignored leak, the control address printed).
