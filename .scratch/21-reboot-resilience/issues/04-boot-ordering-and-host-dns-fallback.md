# 04: Boot ordering, late-dependency tolerance, single-owner host DNS with a real fallback (staged), and the runtime-state audit

**What to build:** After a reboot, dependencies arriving late no longer matter and host name resolution can't be taken down by a container. Docker is ordered after the Tailscale daemon (ordering only, never a hard dependency); every service is shown to tolerate a dependency that arrives late; and — starting from a fresh, attended capture of the live resolver chain — exactly one component owns the host's resolver configuration, with a fallback that is actually consulted and a bounded delay when AdGuard is stopped or *hung*. The ownership change ships **disabled** and is enabled only by the attended drill. A written audit lists everything else the playbook sets up in runtime-only or order-dependent state, each item fixed or recorded as accepted.

## Implementation notes

**The attended read-only capture (AC 1), 2026-09-20.** Run by the agent over the operator's standing SSH authorization, read-only commands only (tailnet name redacted). Findings: `/etc/resolv.conf` was a **regular file generated by Tailscale** (`nameserver 100.100.100.100`, a tailnet search suffix); `resolvectl` reported `resolv.conf mode: foreign` with a global `DNS Servers: 127.0.0.1` (the AdGuard handover's drop-in) and the provider's two DHCP nameservers on the uplink link; `tailscale debug prefs` showed `CorpDNS: true` and — unrelated to DNS but relevant to epic 23 — `AdvertiseRoutes: [0.0.0.0/0, ::/0]` (the main node had been made an exit node by hand, invisible to the playbook); `tailscale dns status` confirmed Tailscale was handling DNS on the host. So host lookups went `libc → Tailscale's resolver → the tailnet nameserver (AdGuard on this host) → Quad9`, and the playbook's handover rewrote resolv.conf on every deploy. Also captured: forwarding sysctls persisted for both families by the Tailscale installer (`/etc/sysctl.d/99-tailscale.conf`), `docker.service` having **no** ordering against `tailscaled` (its `After=` listed only `containerd`, `network-online.target`), `ssh.socket` enabled, and `caddy-relay` with `RestartCount=0` since the last boot.

**Decisions**
- **Owner: the repo's handover (systemd-resolved), not Tailscale.** Staged behind `host_dns_resolver_owner_enabled` (default `false`, in `group_vars`, read by both the `tailscale` and `adguard` roles). *Disabled:* a routine deploy leaves a working resolver exactly as found — the `resolv.conf` repoint now runs only when the current file would be broken by the stub listener being off (missing, a symlink to the stub file, or a regular file still naming `127.0.0.53`); the decision is an evaluable variable and its truth table is tested against synthetic host states. *Enabled (by the drill):* `tailscale set --accept-dns=false`, wait for Tailscale to release the file, repoint to resolved's non-stub file, restart resolved. Other tailnet devices are unaffected.
- **Fallback that is actually consulted:** the resolved drop-in lists `127.0.0.1` first, then `host_dns_fallback_servers` as *ordinary* `DNS=` servers — `FallbackDNS=` is ignored while any `DNS=` is set. **Bounds** (stated, asserted in the drill): AdGuard stopped ≈ 0 s extra (nothing listens, the kernel answers "port unreachable"); hung ≤ ~5 s extra per lookup (glibc default). A tighter bound would need a static `resolv.conf` with `options timeout:1`, considered and not chosen.
- **`tailscale up` restates `--accept-dns` explicitly in both switch states**, so a later re-login cannot fail on "requires mentioning all non-default flags" — including after the switch is turned back off (a review finding).
- **Docker is ordered after `tailscaled` by an ordering-only drop-in** (`After=` only; the test forbids `Requires/Wants/BindsTo/PartOf/Requisite/Upholds/Conflicts`), so a stopped or failed Tailscale can never keep Docker from starting.
- **Late-dependency tolerance and the runtime-state audit** are in `docs/reboot-resilience.md`: a per-service dependency table with stated bounds (Docker's restart backoff caps at 60 s) — a test fails if an enabled service has no row — and the audit table. Convergence is *documented* here; *observing* it (notably `hermes-agent`, whose internal retry behavior is not statically verifiable) is a drill step (#06).

**Tests** (`tests/check-boot-ordering.sh` + `tests/test_boot_ordering.yml`, wired into `tests/lint.sh`): the repoint decision table (8 host states × switch), rendered drop-ins for both switch values, gating/ordering of the handover tasks, the doc's coverage; `tests/check-adguard-dns.sh` follows the drop-in into its template. Mutation-checked: forcing "always repoint" (today's fight-with-Tailscale behavior) fails the decision table. **Not verifiable here (drill #06):** real systemd ordering, Tailscale actually releasing `resolv.conf`, the measured stopped/hung delays, real convergence after a reboot.

**Review round 1 (three blocking items; fixed).** The reviewer traced the switch-**off** path task by task on both the live host's state (Tailscale-generated `resolv.conf`) and a fresh Ubuntu host: it leaves the live resolver untouched and still fixes a fresh one. Blocking findings, all fixed: (1) the wait for Tailscale to release `resolv.conf` had `failed_when: false`, so a timeout would silently repoint anyway — exactly the race the wait exists to prevent; it now **fails the play** if Tailscale still owns the file after the retries; (2) the tests injected synthetic results and never ran the tasks' real shell commands (a stub regex changed to `127.0.0.99`, and a wait grep changed to "generated by nothing", both went unnoticed) — the guard now **extracts and executes the real `cmd:` strings against fixture files** (stub file → match, Tailscale file → no match, missing file → no match; Tailscale-generated → still owned, released → free) and asserts the failure condition; (3) the docs wrongly listed the provider's DHCP resolvers as a further tier — glibc reads only three `nameserver` lines, so with the switch on they are exactly AdGuard and the two fallbacks and **the provider's resolvers drop out of the path** (documented, with the design consequence, the loss of MagicDNS names, and that turning the switch back off does not revert Tailscale — plus the manual rollback). Also applied: the switch-off drop-in is now **byte-identical** to the one the role has always written (comments moved to Jinja comments, `DNS=` built with `join`), so a routine deploy no longer rewrites it or restarts systemd-resolved once; the ordering drop-in path is asserted exactly. All four mutations the reviewer found or that regress the fix (stub regex, wait grep, `.disabled` rename, `failed_when: false`) now fail the guard.
