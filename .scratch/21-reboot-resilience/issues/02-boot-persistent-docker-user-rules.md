# 02: Boot-persistent, atomic DOCKER-USER rules and the boot firewall unit

**What to build:** After this ticket a reboot or a Docker restart reloads the restricted-port rules by itself, and a routine deploy repairs a missing chain even when nothing about the rules changed. The port classes are rendered once, for both IP families, into a single ruleset; every deploy compares the live chain with it and loads it atomically when they differ (the chain is never half-built or empty, even momentarily), and a boot firewall unit loads that same rendering at boot and whenever Docker restarts. The imperative per-rule tasks are removed. SSH, UFW and the INPUT chain are untouched. The fail-closed coupling ships **disabled** until the attended drill enables it.

## Implementation notes

**What was built** (all in the `tailscale` role, the single owner of the perimeter — there is no separate firewall role):
- The 19 imperative `iptables` tasks are gone. The port classes (`group_vars/all/main.yml`, unchanged) are rendered **once per IP family** into restore-format files (`docker-user.rules.v4.j2` / `.v6.j2`) — one table, one declared chain, append-only, no reference to UFW, INPUT or the SSH port.
- **One loader** (`hermes-docker-user-rules apply|test|status`) is the only way rules reach the kernel; both the deploy and the boot unit call it. `apply` validates *both* families with `--test` before loading either (so a bad file can never leave one family updated), then loads each with `iptables-restore --noflush`, which the spike showed replaces only the declared chain, in one nftables transaction.
- **Boot unit** `hermes-docker-user-firewall.service`: `Type=oneshot`, `RemainAfterExit=yes`, `Before=docker.service`, `PartOf=docker.service`, `WantedBy=multi-user.target docker.service` — exactly the wiring ticket #01 recommended (rules loaded *before* the daemon starts; measured safe 10/10 where "after the API answers" was unsafe 10/10). It has no `ExecStop`, asserted by a test (`PartOf=` propagates a Docker stop to it; a flush there would empty the chain on every Docker restart).
- **A deploy heals an unchanged artifact:** the load task snapshots the live chain (`status`), applies, snapshots again and reports *changed* only when the live chain actually differed — independent of whether any file changed or the unit considers itself started. This is the original fault ("files unchanged, chain empty").
- **Staged fail-closed coupling:** `tailscale_docker_user_firewall_fail_closed` (default `false`) controls a `docker.service` drop-in with `Requires=`/`After=` on the unit. While `false` the drop-in is **removed** (`state: absent`), so a routine deploy cannot put an untested fail-closed unit on production; the attended drill (#06) enables it. Documented in the README, including that `--skip-tags tailscale` skips *updating* the rules and unit but never removes an installed unit.
- Reloading by hand: `hermes-docker-user-rules apply`. **Do not `systemctl restart` the unit** — with the coupling on, `docker.service` requires it, so a restart bounces Docker and every container (documented in the unit's comment and the README, and pinned by a test).

**Tests** (`tests/check-docker-user-firewall.sh`, wired into `tests/lint.sh`): assert on the *rendered rules' behavior* — for a custom and the default port-class fixture: tailnet-accept-then-drop ordering per restricted port (TCP and UDP, both families), public ports accepted with no drop, an unclassified port gets no rule, Syncplay allowlist (IPv4 only; empty list = blocked; IPv6 always dropped), bridge/established traffic before any classification; blast radius (one table, one chain, only `-A`, no jump into UFW/INPUT/OUTPUT/FORWARD, no port 22); byte-stable rendering; unit properties; the staged coupling. **Mutation-checked:** swapping accept/drop order, smuggling a flush into the ruleset, and defaulting the coupling to enabled each turn the guard red. A guarded **live** section runs the real loader in the disposable epic-21 container: syntax-valid for both families, idempotent, *heals a flushed chain*, and leaves a chain it does not own untouched. The two older tests that pinned the old task names (`check-custom-services.sh`, `check-adguard-dns.sh`) now pin the templates and the class variables instead; `check-tailscale.sh`'s guarded live block gained the heal case (chain emptied, files unchanged, redeploy restores it).

**Not verifiable here — operator-validated in the attended drill (#06):** that the rules and unit survive a *real* reboot and a *real* Docker restart, real systemd ordering (`Before=`, `PartOf=`, `WantedBy=docker.service`, `Requires=`), and that the deploy's tasks work on the real host (they need root and systemd; the loader and the rendering are what the tests exercise). Verified with `systemd-analyze verify`: the rendered unit is syntactically valid (its only complaint is the loader binary, which exists on the VPS).

**Findings from the spike applied:** `iptables-restore` 1.8.11 (nf_tables) has **no `-w`/`--wait` flag**, so none is used. The loader is safe to run at any time because `--noflush` is atomic.

**Review round 1 (changes required; fixed).** The reviewer confirmed the rendered rules are *behaviorally identical* to the 19 old tasks for both families (same rules, same order, same source forms) and found no exposure window, but showed three of my tests were text-greps that missed real regressions. Fixed with behavioral tests — each of the reviewer's three mutations now fails the guard:
- **Inverted drop-in gating** (would ship the untested fail-closed coupling to production): the test now *evaluates the tasks' real `when:` expressions* for both switch values and asserts install/remove are exclusive and correct.
- **A heal task that always says "changed"**, and
- **Deleting the IPv6 pre-validation**: the live section now *executes the deploy's own heal task* (rendered from the YAML, run under `sh` in the disposable container): silent when nothing drifted, `CHANGED` and restored when the chain was emptied; and a corrupt v6 file must leave even a valid-but-different v4 file unapplied (validate-both-first).
- Also: the default render now verifies *every* class for *both* families (public/restricted TCP/UDP incl. the templated port); each rendered file is syntax-checked (`validate:`) before it is installed, so a bad file never lands on disk (the duplicate separate validate task was dropped); a stale "flushed and rebuilt" comment fixed; the loader header and README now say plainly that the two families are two transactions validated together, and that what is always live is the unit's `Before=/PartOf=/WantedBy=docker.service` wiring (only `Requires=`/`After=` ships disabled); a missing podman image now produces a loud banner rather than a quiet skip.

**Review round 2 (one blocking gap; fixed).** Round 2 confirmed all round-1 fixes work (each mutation replayed by the reviewer was caught) and found one more: a heal task that lost `set -eu` swallows a *failed* rule load (its last command is an `if`, which returns 0), so the deploy would report success with the chain never loaded — the original silent failure, in the security-critical path. Now pinned by a live failure-propagation test (`apply` against a corrupt ruleset must fail the *heal task itself*) plus a static `set -eu` assertion; the per-family `validate:` mapping (v4 file ↔ `iptables-restore`, v6 ↔ `ip6tables-restore`) is now evaluated for both values rather than grepped. A note was added that `flush_handlers` also runs earlier roles' queued handlers at that point.

**Review round 3 (three gaps in the security-critical path; fixed).** Round 3 confirmed round 2's fixes and showed three regressions the guard would still miss: (1) **nothing verified the IPv6 load is `--noflush`** — dropping it would make `ip6tables-restore` flush the *whole* v6 filter table (UFW's and Docker's chains) on every deploy and boot; (2) an `After=docker.service` in the boot unit contradicts `Before=docker.service` (an ordering cycle systemd breaks by dropping a job, possibly leaving Docker up without rules); (3) a loader installed `0666` (root-executed boot code, world-writable). Now pinned: static checks that all four restore lines in the loader are the exact `--noflush` / `--noflush --test` forms and that the loader has `set -eu`; a live check that a foreign **v6** chain survives `apply`; a check that the unit has no `After=`/`Requires=`/`Wants=`/`BindsTo=` on `docker.service`; and installed owner/mode assertions (root-owned, never group/world-writable) for the rules directory, rule files, loader and unit. Also `status` no longer swallows real failures — only "chain missing" reads as empty — with a live check that a deleted chain is recreated by `apply`. Each of the three missed mutations was replayed and now fails the guard.

**Review round 4: PASS.** No blocking issues; all acceptance criteria met; the reviewer replayed the round-3 mutations plus a swapped-restore-tool mutation (caught by the live section) and confirmed the loader's `status` code is correct POSIX sh and that the nf_tables backend does not take the xtables lock (so no `-w`). Non-blocking suggestions taken: each restore tool is tied statically to its own family's file; `SuccessExitStatus=` / `ExecStart=-` are forbidden in the unit (either would make a failed load look active and defeat fail-closed once enabled). Known limit, accepted: the loader-tool↔file pairing is *also* covered by the live section, which needs podman and the spike image — its absence prints a loud banner. Four review rounds in total (one earlier attempt was lost to an API limit before reporting and did not count).
