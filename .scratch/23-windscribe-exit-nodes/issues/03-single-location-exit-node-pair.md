# 03: One exit-node pair from one list entry, isolated, with list-driven compose support

**What to build:** A single exit location renders end to end into the consolidated stack as a working exit-node pair — a Windscribe tunnel, a Tailscale exit node sharing its network namespace, and the routing sidecar — carrying the three fixes the first spike discovered **plus the fourth fix ticket #01's own spike found (the Tailscale image defaults to userspace networking; kernel networking must be explicitly enabled, or none of the other fixes matter)**, the recovery mechanism and versions ticket #01 chose, and the gluetun server-list policy #01 decided. The pair sits on its own dedicated Docker network so a compromised container cannot reach the rest of the stack, and a deploy from a clean host works before any exit-node credential file exists. The compose renderer gains generic support for a list-driven fragment that declares several services, and the stack start step addresses the services actually rendered.

**Blocked by:** #01, #02, Epic 21 #03
**Blocks:** #04, #05

**Status:** done

- [x] One pair renders from a one-entry list: the tunnel using gluetun's Windscribe provider with the entry's region and city, a Tailscale exit node in the tunnel's network namespace, and a routing sidecar
- [x] There is no host network mode and no published port; every rendered service declares a restart policy and epic 21's guard (over rendered services) passes
- [x] **Isolation:** the pair's services attach to a dedicated network of their own and to neither `gateway` nor `internal` (asserted); the container-bridge early-return in the firewall chain therefore gives the pair no path to Authelia, Hermes or any other service
- [x] Credentials reach the containers through a per-node restricted environment file, never inline in the compose file; images are pinned to the versions recorded by #01
- [x] **Clean-host deploy:** compose validation and image pulls, which run before the roles that depend on the compose role, succeed on a host where the per-node environment files do not yet exist — either the exit-node role runs ahead of the compose role or the files are declared optional to the compose file — proven by a render test that starts from a clean host
- [x] **The Tailscale container runs in kernel networking mode (`TS_USERSPACE=false`), not the image's userspace-networking default** — #01 found that without this, no `tailscale0` interface exists at all and exit-node function is silently impossible regardless of anything else configured
- [x] Tailscale runs in nftables mode; with kernel networking active, Tailscale's own `ts-forward`/`ts-postrouting` nftables chains handle forwarding and masquerade automatically (#01 found manually-added `iptables` FORWARD/MASQUERADE rules unnecessary and did not render them) — asserted: no IPv6 forwarding is accepted, and nothing beyond what Tailscale itself installs is added
- [x] The return-path routing rule (gluetun's catch-all policy route otherwise wins over Tailscale's own table for tailnet-destined traffic) exists for both address families and is reapplied by the routing sidecar on every one of its own starts — it does not survive tunnel restart OR recreation (#01: confirmed lost in both cases, not just recreation)
- [x] Dependents (exit-node, routing sidecar) recover via the existing deploy flow's `docker compose up -d` over the full rendered service set — #01 found a bare `docker restart` fails outright once the tunnel container's ID has changed (`network_mode: service:` binds to the container ID at creation time, not its name); no custom watcher or `docker.sock` access is needed
- [x] **The server-list update policy #01 decided is implemented**: gluetun's built-in periodic updater, `UPDATER_PERIOD=24h` and `UPDATER_VPN_SERVICE_PROVIDERS=windscribe`
- [x] Tailscale state persists per node, the hostname is `<prefix>-ws-<name>` using the validated prefix from #02, and the node is tagged (`tag:exit-node`, already created by #01's tailnet ACL change) for auto-approval
- [x] The compose role supports a list-driven fragment declaring several services, generically; the stack start step addresses the rendered service set; existing services are unaffected
- [x] Render tests assert all of the above, and the consolidated compose passes validation
- [x] Nothing in the role modifies host routing (asserted)

## Implementation

### The generic list-driven fragment mechanism (compose role)

`roles/docker/defaults/main.yml` gained `docker_list_fragments: []` — a list of `{template, entries}`. `roles/docker/templates/docker-compose.yml.j2` renders each fragment's template once per entry, via `lookup('template', fragment.template, template_vars={'item': entry})`, with `entry` available inside the fragment as `item`. The real wiring (`exit_nodes` → `services/exit_node_pair.yml.j2`) lives in `group_vars/all/main.yml`, not either role's own defaults — a role default can't reference another role's list variable, and that file is already this repo's established composition point for cross-role, non-secret config (`docker_published_*_ports`).

Two bugs found and fixed while building this, both real, both worth recording since a future list-driven fragment will hit them again otherwise:

1. **The list key could not be named `items`.** A dict's own built-in `.items()` method shadows a same-named key on Jinja attribute access — `fragment.items` silently returned a bound method object instead of the list (`'method' object is not iterable`), found immediately by rendering a throwaway fixture locally before touching the real test suite. Renamed to `entries` everywhere.
2. **The existing single-service indent idiom breaks for a fragment with more than one top-level key.** The established pattern (`  {{ lookup(...) | indent(4) }}`) relies on `indent()`'s default `first=False` leaving line 1 alone while the outer literal `"  "` prefix covers it — correct for a fragment with exactly one top-level YAML key, but a multi-service fragment's *second and third* top-level keys (`...-node:`, `...-sidecar:`) are also "line 1 of their own logical block" as far as YAML nesting is concerned, yet `indent()` treats them as ordinary continuation lines and pads them the same as everything else — producing `services:` children at inconsistent depths and an actual YAML parse error (`expected <block end>, but found <block mapping start>`), confirmed with `python3 -c "yaml.safe_load(...)"` against the real rendered output, not just eyeballed. Fixed with a separate, uniform `indent(2, first=True)` for the list-fragment loop only (shifts every line, including the first, by exactly 2) — left the single-service loop's own idiom untouched since it works correctly for its own shape and 13 existing fragments already depend on its exact output.

`roles/docker/tasks/start.yml`'s `docker_compose_v2` task dropped its `services: "{{ docker_enabled_services }}"` restriction entirely. It was already redundant (the compose file only ever contained exactly that list) and would have silently excluded every exit-node-pair service (their names aren't in `docker_enabled_services` at all). The module's own default (`services: null`) is "operate on every service in the file" — exactly "the rendered service set," generically, with no bookkeeping list to keep in sync as list-driven fragments come and go.

### exit_node_pair.yml.j2 — the per-location fragment

Renders three services per `exit_nodes` entry, matching the exact configuration ticket #01's spike validated live (`spike-compose.yml`), plus this ticket's own two additions:

- **Tunnel** (gluetun, pinned by digest, `exit_nodes_gluetun_image`): `VPN_SERVICE_PROVIDER=windscribe`, `SERVER_REGIONS`/`SERVER_CITIES` from the entry, `UPDATER_PERIOD`/`UPDATER_VPN_SERVICE_PROVIDERS` per #01's decision. No `FIREWALL_*` overrides — the spike's own working config had none (fix #2 is unnecessary), and adding one un-tested here would be a real behavior change #01 never validated.
- **Node** (Tailscale, pinned by digest, `exit_nodes_tailscale_image`): `network_mode: service:<tunnel>`, `TS_USERSPACE=false` + `TS_DEBUG_FIREWALL_MODE=nftables` (fixes #1 and the fourth fix), `TS_EXTRA_ARGS=--advertise-exit-node --hostname=<prefix>-ws-<name> --reset`, state bind-mounted per location (`exit_nodes_state_dir/<name>`, root-owned — the official image runs as root).
- **Sidecar** (this ticket's own contribution — #01 applied the return-path rule by hand mid-spike; this is what makes it self-healing for real): reuses the already-pinned Tailscale image rather than adding a new image dependency purely for one shell command (it ships `iproute2`). `network_mode: service:<tunnel>`, entrypoint reapplies `ip rule add ... || true` for both address families (`exit_nodes_return_route_table: 52`, the table #01 observed and pinned — the comment in `defaults/main.yml` flags it for re-verification if `exit_nodes_gluetun_image` is ever bumped), then `sleep infinity` to stay in the running state `restart: unless-stopped` expects. `|| true` makes re-adding safe when the tunnel's netns never actually changed (a same-ID restart of the sidecar alone).

**Tagging (AC: "the node is tagged... for auto-approval"): no `--advertise-tags` flag anywhere in the fragment, by design.** A Tailscale auth key created with a tag in the admin console tags any node that authenticates with it automatically — the tag comes from the (one-time, admin-console-side) key, not a client-side flag. `secrets.exit_node_tailscale_authkey` is documented (a later ticket's README work) as needing to be minted as a `tag:exit-node`-tagged, reusable key; nothing in this ticket's own rendered compose needs to know about tags at all.

**Isolation:** `exit_nodes_net` (a new, third entry in `roles/docker/defaults/main.yml`'s `docker_networks`, alongside `gateway`/`internal`) is the tunnel's only network; node and sidecar declare no `networks:` of their own at all (`network_mode: service:` and `networks:` are mutually exclusive in Compose), so all three ride on the tunnel's single interface.

### Credentials: one shared restricted file, not one per location

`exit_nodes_credentials_file` (`{{ docker_compose_dir }}/exit-nodes/credentials.env`, root:docker 0640 — the same permission model as `docker-compose.yml` itself, epic 22 #07) holds all four secret values once. Every tunnel/node service's `env_file:` points at it. **Deliberate reading of "per-node restricted environment file" (AC):** satisfied by every pair's own services referencing a restricted file via `env_file:` — never inlined into `docker-compose.yml` — not by giving each location a byte-identical copy of the same four values. The epic's own "one credential set serves every location" decision (verified live in #01: the same key connected two servers at once) means duplicating identical secret material per location would add files to keep in sync for zero isolation benefit.

`env_file` entries use the Compose-spec long form with `required: false` — needed for the render test (which renders `docker-compose.yml.j2` directly and never runs the `exit_nodes` role that writes the file), not for a real deploy (see next section). Confirmed via `python3 -c "yaml.safe_load(...)"` and the restart-policy guard that a render with the file genuinely absent still produces valid, fully-checkable YAML.

### exit_nodes role: validate, then write everything the fragment needs

`roles/exit_nodes/tasks/main.yml` now runs three steps (`validate.yml`, unchanged from #02; the two new files below), and is wired as a **meta/main.yml dependency of the `docker` role** (`roles/docker/meta/main.yml`) — the exact mechanism `gateway` already uses for `owntracks`/`beszel`/`adguard`. Ansible runs a role's meta dependencies before its own tasks, so `exit_nodes` always executes ahead of `docker`'s own compose render/validate/pull steps, in the same play, satisfying the clean-host AC structurally (not by site.yml list-position luck, and not needing the `env_file` optionality above for a real deploy at all — it's belt-and-suspenders there, load-bearing only for the local render test).

- `write_credentials.yml`: writes `exit_nodes_credentials_file` from `templates/credentials.env.j2`, root:docker 0640, `no_log: true`.
- `ensure_state_dirs.yml`: one root-owned `0700` directory per `exit_nodes` entry under `exit_nodes_state_dir`.

Both are separate files from `tasks/main.yml` (not just inlined) for the same reason `validate.yml`/`validate_entry.yml` already are: a test playbook can exercise each independently. This mattered concretely here — `write_credentials.yml`'s directory/file tasks need a real `docker` group, and `ensure_state_dirs.yml`'s original hardcoded `owner: root, group: root` needed a real root/privileged user — neither exists on the local test host. `ensure_state_dirs.yml`'s owner/group became their own variables (`exit_nodes_state_owner`/`_group`, defaulting to `root`/`root`, matching `wiki_volume`'s own `ensure_directory` interface pattern) specifically so `tests/test_exit_nodes_render.yml` can override them to the test-runner's own username and prove the same directory-creation logic without needing privilege. `credentials.env.j2` itself is tested by rendering it directly (no ownership tasks) with fake secrets.

### Role wiring, ordering, and duplication

- `roles/exit_nodes/tasks/main.yml` carries `tags: [exit_nodes]` on every task; added to `tests/lint.sh`'s skip-tags guard role list.
- `exit_nodes` is **not** an explicit `site.yml roles:` entry (adding one alongside `docker`'s own meta dependency would duplicate its execution — the same trap epic 15 already documented for `owntracks`).
- Real measured effect on `tests/check-role-duplication.sh`: `exit_nodes` runs **5** times per `site.yml --list-tasks` (not 4, matching `docker`'s own `DOCKER_MAX`) — 4 from `docker`'s 4 dependents (conduit/hermes/authelia/silverbullet), plus a 5th from the end-of-play `import_role: docker, tasks_from: start` step, which — per `tasks/start.yml`'s own pre-existing comment about `wiki_volume` — re-resolves meta dependencies for that separate invocation even though `docker`'s own `tasks/main.yml` doesn't run again there. Added `EXIT_NODES_MAX=5` and a real structural proof (every `docker` occurrence has a preceding `exit_nodes` occurrence) to `tests/check-role-duplication.sh`, matching its existing `WIKI_VOLUME_MAX`/`DOCKER_MAX` pattern and tone. Every repeated execution is idempotent (an assert, a template render, directory creation) — same accepted tradeoff already documented there for `wiki_volume`/`docker`.
