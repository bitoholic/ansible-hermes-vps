### Live attended validation: what actually happened

Driven live, together with the operator, in one session. In order:

1. **Prerequisites.** Operator generated a Windscribe WireGuard config and provided `WINDSCRIBE_PRIVATE_KEY`/`WINDSCRIBE_ADDRESS`/`WINDSCRIBE_PRESHARED_KEY` plus a reusable `EXIT_NODE_TAILSCALE_AUTHKEY`, filled via `scripts/secrets fill` (operator's own terminal, never pasted into chat). ACL updated with an `autoApprovers.exitNode: ["tag:exit-node"]` stanza — the operator's chosen mechanism over manual per-node console approval, since it's purely additive and can't itself cause an access lockout.
2. **ACL sequencing — the one real deviation from the AC as written.** The operator applied (saved) the ACL policy edit in the Tailscale console *before* asking for a pre-check, rather than after a previewed, confirmed-safe change. Once told, re-verification proceeded immediately per the AC's spirit (an alternate SSH path over the public address was already in hand from earlier work; existing access was re-checked right after). This is recorded here plainly rather than retroactively marking the AC as followed to the letter.
3. **A real SSH-over-tailnet regression was found and fixed.** After the ACL save, SSH over the tailnet IP stopped working (public-IP SSH still worked, and every other tailnet-routed service was unaffected). Diagnosed via `sudo journalctl -u tailscaled` (reachable over the still-working public-IP path): Tailscale's own embedded SSH server ("Tailscale SSH," a feature distinct from real OpenSSH, previously seen as a dismissed-as-harmless health warning back in ticket #01) was intercepting all tailnet-sourced port-22 connections against an undefined `"ssh"` ACL policy dimension — **not** a regression in the `acls` rules themselves, which were materially unchanged; `autoApprovers` is purely additive and cannot cause this. Fixed, with the operator's explicit choice between two options, via `sudo tailscale set --ssh=false` on the VPS; confirmed fixed by the operator immediately after.
4. **Real deploy.** Check-mode reviewed first, then applied for real: `ok=210 changed=30 unreachable=0 failed=0`.
5. **Live verification.** `scripts/verify-exit-nodes.sh` run against the real fleet found and fixed three real bugs in the *script itself* (stdin-consumption loop bug that silently skipped warsaw; a false-FAIL in the isolation check that didn't account for how `network_mode: service:` dependents actually report their networks; `curl` unavailable in gluetun's Alpine image, switched to `wget`) — full history in ticket #06's own notes. Final live run: 38 passed, 0 FAILED.
6. **Phone test.** Operator tested both locations from their phone directly: both exit nodes work correctly (reported "both exit nodes work ok").
7. **Kill-switch + recovery test — found a real, previously-undiscovered gap.** `docker stop` on the london tunnel, confirmed via a dependent container that egress drops (`Network unreachable`, no leak even though the dependents stay in a stale netns — gluetun's kill switch holds regardless). `docker start` on the tunnel alone (not the dependents) revealed: **node and sidecar do not automatically recover** when only the tunnel restarts while they themselves stay running — they're left attached to the tunnel's OLD, now-orphaned network namespace indefinitely, confirmed via `/proc/<pid>/ns/net` inode comparison. `docker compose up -d` does not detect or fix this (container IDs never change). Given the choice to record this as a known limitation or fix it now, the operator chose to fix it as part of this epic.

### The recovery-gap fix: three rounds, two real bugs found deploying it live

Added a debounced TCP-probe `HEALTHCHECK` to both `node` and `sidecar` (`roles/docker/templates/services/exit_node_pair.yml.j2`'s new `recovery_healthcheck()` macro, new vars in `roles/exit_nodes/defaults/main.yml`): on 3 consecutive 30s-interval failures to reach `1.1.1.1:443`, the healthcheck signals its own container's PID 1, which `restart: unless-stopped` then picks up as an ordinary exit — and a normal container restart correctly re-resolves `network_mode: service:tunnel` to the tunnel's *current* namespace (ticket #01's own confirmed behavior for a dependent's own restart).

Getting this actually working live took three attempts:

1. **First deploy: Docker Compose's own variable interpolation silently broke the script.** Compose resolves `$VAR`/`${VAR}` in compose-file content *before* a container ever sees it — the healthcheck's bare `$n` and `$(cmd)` were being resolved against Compose's own (unset) variable namespace and replaced with empty strings. Confirmed via `docker inspect` on the live container: `echo $n > ...` had become `echo  > ...`. Fixed by escaping every literal `$` meant for the container's shell as `$$`, Compose's documented escape for a literal dollar sign.
2. **Second deploy (after the `$$` fix): node recovered correctly, sidecar did not.** Polling the live fleet after a tunnel-only restart showed `node` self-restart and go healthy within ~90 seconds, exactly as designed — but `sidecar` stayed `unhealthy` indefinitely (confirmed failing streak climbing past 10) and never restarted. Root cause, confirmed by direct experiment on the live container: a process that is **PID 1 of a PID namespace is immune to any signal it has not explicitly installed a handler for — including SIGKILL — when that signal is sent by another process *inside the same namespace*** (`pid_namespaces(7)`). `docker exec exit-node-london-sidecar kill -9 1` did nothing at all, repeatedly, while an external `docker kill --signal=SIGKILL` from the host worked instantly. Node's PID 1 (Tailscale's own `containerboot`) happens to already trap SIGTERM for its own graceful shutdown, which is why it recovered; the sidecar's PID 1 was a bare `exec sleep infinity` with no handler of its own. Fixed by having the sidecar's own command `trap 'exit 0' TERM` and `wait` on a backgrounded `sleep` instead of `exec`ing into one — installing a handler is what makes the kernel treat the healthcheck's internal signal as handled rather than exempt.
3. **Third deploy: both node and sidecar confirmed self-healing, live, end to end.** Full kill-switch/recovery test repeated from scratch on the london pair: tunnel stopped (kill switch confirmed holding), tunnel restarted, node and sidecar deliberately left untouched. Both went `unhealthy` after the tunnel restart, then both self-restarted on their own (`RestartCount` incremented; new container start timestamps ~72–73 seconds after the tunnel came back) and went `healthy` again — and `nc -zv 1.1.1.1 443` succeeded from inside *both* containers afterward with zero manual intervention. Debounce counter files (`/tmp/hermes_recovery_fails`) confirmed cleared on the successful probe in both containers.
